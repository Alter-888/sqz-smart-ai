# 04 · 接口设计（REST + SSE）

> 本文只做**增量**：`[沿用]` 一个字不改，`[改]` 是既有接口的行为变化，`[新增]` 是本轮新加。
> 路径、参数、权限注解全部对照现有 `ChatController` / `KnowledgeController` / `DashboardController` 核实，**不要照着印象写**。

---

## 一、对话（核心链路）

### 1.1 取一次性 ticket `[沿用]` `POST /ai/chat/stream-ticket`

响应：`{ "code": 200, "data": { "ticket": "8f3c..." } }`
ticket 存 Redis，**60 秒有效、用后即删**（`ChatService.createOneTimeTicket` / `validateAndConsumeTicket`）。作用是避免把长期 JWT 放进 SSE 的 URL 里。

### 1.2 SSE 流式对话 `[改]` `GET /ai/chat/stream?message={}&sessionId={}`

**注意是 GET + query 参数**（SSE 只能用 GET），不是 POST。已有的入参校验保留：消息非空、长度 ≤5000、`sessionId > 0`、`validateSessionOwnership`。

改造点只有一处：内部从"直接调 `chatClient`"变成"调 `ChatOrchestrator.handle()`"，并多推两类事件。

事件清单（**`name` 为空表示走默认事件，前端按现有方式收**）：

| 事件 name | 数据 | 说明 |
|-----------|------|------|
| `intent` `[新增]` | `{"intent":"PRODUCT","agentId":"sales-advisor","source":"rule"}` | 路由一出结果**立刻**推，前端显示"导购助手正在处理…"。这是压低感知延迟最便宜的一招 |
| `tool_call` `[沿用]` | `{"toolName":"searchProducts","description":"正在搜索商品"}` | 工具调用过程 |
| `card_data` `[沿用]` | `{"cardType":"product","items":[...]}` | 结构化卡片 |
| `data_changed` `[沿用]` | `{"types":["cart"]}` | 通知前端刷新对应页面数据 |
| `rag_source` `[沿用]` | `[{"title":"退货政策","category":"POLICY","knowledgeId":"33"}]` | 溯源。改造后这份数据来自**唯一一次检索**，与真正喂给模型的块一致（03 §五） |
| `pending_action` `[新增]` | `{"actionId":12,"toolName":"cancelOrder","summary":"取消订单 ORD20250001","expireAt":"2026-09-03T10:20:00"}` | 高危操作待确认，前端渲染确认卡片（02 §十三） |
| `message_id` `[沿用]` | `{"messageId":123}` | 供赞/踩定位 |
| *(无 name)* `[沿用]` | 回复正文字符串 | 现有实现是 `emitter.send(SseEmitter.event().data(response))`，**没有事件名**，前端靠默认 message 事件接收 |
| *(无 name)* `[沿用]` | `[DONE]` | 结束标记，同样没有事件名 |

> ⚠️ 正文和 `[DONE]` **不要顺手给它们加上事件名**。前端现在是按默认事件收的，加了 name 就收不到了。这属于"看起来更规范但会直接弄坏功能"的改动。
> ⚠️ 当前实现是"整段回复一次性推送"（内部用 `.call()` 而非 `.stream()`，为了让工具调用链路稳定）。改造不动这个决定——`intent` 和 `tool_call` 事件已经让用户在等待期间有反馈了。

### 1.3 高危操作确认 `[新增]`

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/ai/chat/pending-action/{id}/confirm` | 确认执行。四道校验：归属本人 / 状态 `PENDING` / 未过期 / 工具在 `hitl-tools` 白名单内（02 §13.4） |
| `POST` | `/ai/chat/pending-action/{id}/cancel` | 用户放弃，状态置 `CANCELLED`，不执行 |
| `GET` | `/ai/chat/pending-action/list?status=PENDING` | 查自己的待确认操作（刷新页面后仍能看到卡片） |

请求体：**只有路径上的 `id`**。绝不接受前端传类名、方法名或参数——那等于把反射入口开放给调用方。

响应（confirm 成功）：
```json
{ "code": 200, "msg": "操作已执行", "data": "订单 ORD20250001 已取消，退款将在 1-3 个工作日到账" }
```

失败一律走 `ServiceException`，前端按现有 `msg` 展示。越权时返回的是"操作不存在"而不是"无权限"，**故意不泄露该 id 是否存在**。

### 1.4 非流式对话 `[改]` `POST /ai/chat/send`

请求体：`{ "message": "...", "sessionId": 36 }`（沿用）。
改造点：内部同样改走 `ChatOrchestrator`；`ChatService.detectCategoryFilter` 这个已标 `@Deprecated` 的关键词过滤方法**整个删除**，过滤改由路由决定（03 §二）。

这条路径没有 `SseEmitter`，所以 `ChatContext.getEmitter()` 是 null——`pushIntent` 和 `pending_action` 事件推送都必须先判空（02 §九已处理）。**高危操作在这条路径上直接拒绝执行并提示用户改用聊天页面**，因为没有确认卡片可推。

### 1.5 会话与反馈 `[沿用]`

| 方法 | 路径 |
|------|------|
| `POST` | `/ai/chat/session` |
| `GET` | `/ai/chat/session/list` |
| `GET` | `/ai/chat/session/{id}/messages` |
| `DELETE` | `/ai/chat/session/{id}` |
| `PUT` | `/ai/chat/session/{id}/pin` |
| `PUT` | `/ai/chat/session/{id}/title` |
| `PUT` | `/ai/chat/message/{id}/feedback` |

一个字都不用改。

## 二、知识库

### 2.1 知识条目 CRUD `[沿用]`

`GET /ai/knowledge/list`（分页 + `category` 筛选）、`POST /ai/knowledge`、`PUT /ai/knowledge/{id}`、`DELETE /ai/knowledge/{id}`、`DELETE /ai/knowledge/batch/{ids}`、`GET /ai/knowledge/doc/list`。

路径与权限注解都不变，底层从 `SimpleVectorStore` 换成 pgvector（01 §七）。**接口契约不变是这次改造能控制住改动面的关键**：前端知识库页面不用动。

### 2.2 文档上传 `[改]` `POST /ai/knowledge/upload`

`multipart/form-data` 的 `file`。改造点：
- 写入目标从 json 文件换成 PG（01 §7.3）
- 只有确实要支持 PDF/Word 时才引 `spring-ai-tika-document-reader`；**只做 txt 就别提前引依赖**

### 2.3 向量库状态 `[改]` `GET /ai/knowledge/vector-store-status`

从"看 `vectorstore.json` 文件是否存在、多大"改成查 PG 表。返回字段变化：

| 改造前 | 改造后 |
|--------|--------|
| `exists` / `fileSize` / `lastModified` | `vectorCount`（块数）/ `knowledgeCount`（去重后的知识条数）/ `tableSize` / `indexType` / `dimensions` |

SQL 见 01 §十。**必须用 `pgVectorJdbcTemplate`**，用错成默认的 MySQL `JdbcTemplate` 会报表不存在。前端展示文案从"向量文件"改成"向量库规模"。

### 2.4 重建向量索引 `[改]` `POST /ai/knowledge/rebuild-vector?truncate=false`

改造点：新增可选参数 `truncate`（默认 `false`）。

- `truncate=false`：全量重写 `ai_knowledge` 中 `status=1` 的条目。同 id 覆盖，幂等，但**不会删掉已从 MySQL 删除却仍留在向量库里的旧块**。
- `truncate=true`：先 `TRUNCATE public.vector_store` 再重建，用于"知识库删过东西"或"换了 embedding 维度"之后彻底对齐。

把这个语义做成显式参数，而不是让调用方去猜"重建到底会不会清旧数据"（01 §八）。

## 三、指标与评测

### 3.1 在线指标 `[改]` `GET /ai/dashboard/ai-metrics?days=7`

保留现有 5 个汇总值 + 5 条趋势（`toolCallSuccessRate` / `ragHitRate` / `satisfactionRate` / `humanEscalationRate` / `avgTurnsPerSession` 及对应 `*Trend`）。

新增 4 个：`failureRate` / `retryRate` / `timeoutRate` / `p95Latency`。SQL 见 05 §二。

**一个口径变化必须写进接口文档**：`ragHitRate` 改造后只在 `rag_enabled = 1` 的行上统计。因为 `order-service` / `account` 两个域根本不挂 RAG，它们的轮次留在分母里会把命中率算低——那是口径造成的假下降，不是效果退化（02 §四）。

响应新增一个字段 `ragHitRateScope: "rag_enabled=1"`，让前端能在图表上标注口径，避免半年后自己都看不懂为什么数字断层。

### 3.2 离线评测 `[新增]` `/ai/eval/*`

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/ai/eval/run?dataset=v1&remark=P5全文路开启后` | 跑一次黄金集评测，同步返回本次汇总；结果落 `ai_eval_result`。`remark` 是这次跑的目的，配合 `config_snapshot` 才能归因（05 §7.3） |
| `GET` | `/ai/eval/results?pageNum=1&pageSize=10` | 历史评测列表，含 `config_snapshot` 便于同集对比 |
| `GET` | `/ai/eval/golden?pageNum=1&pageSize=10` | 黄金集条目列表 |
| `POST` | `/ai/eval/golden` | 新增黄金集条目 |
| `PUT` | `/ai/eval/golden/{id}` | 修改 |
| `DELETE` | `/ai/eval/golden/{id}` | 删除 |

`POST /ai/eval/run` 是**长耗时同步接口**（100 条 × 检索 + judge 打分）。两个约束：
- 加一把 Redis 分布式锁，**同一时刻只允许跑一个评测任务**，否则并发跑会把模型配额打满、结果也没法归因
- 前端按钮点击后置灰并提示"评测进行中"，不要给用户连点的机会

## 四、权限（照现有约定，别自己发明）

| 接口组 | 权限 | 现状 |
|--------|------|------|
| `/ai/chat/**` | **无 `@PreAuthorize`** | 只要求已登录，靠 `validateSessionOwnership(sessionId, userId)` 做数据隔离。这是现有设计，**新增的 pending-action 接口沿用同一套**：不加权限注解，但必须在 Service 里比对 `user_id`（02 §13.4） |
| `/ai/knowledge/**` | `ai:knowledge:list` / `add` / `edit` / `remove` / `upload` | 沿用 |
| `/ai/dashboard/**` | `ai:dashboard:list` | 沿用 |
| `/ai/eval/**` | `ai:eval:list` / `ai:eval:run` / `ai:eval:edit` `[新增]` | 需要往 `sys_menu` 插菜单和权限字符，脚本见 05 §3.5 |

> ⚠️ 别给 `/ai/chat/**` 补上 `@PreAuthorize("@ss.hasPermi('ai:chat'))`。普通注册用户角色下没有这个权限字符，加上去等于把用户端聊天功能直接关掉。

## 五、前端需要配合的改动（`ruoyi-ui`）

| 位置 | 改动 |
|------|------|
| 聊天组件 | 监听 `intent` 事件 → 顶部显示"{导购/订单/售后/账户/政策}助手正在处理…"；`source` 字段只在开发模式下显示，便于自查路由 |
| 聊天组件 | 监听 `pending_action` 事件 → 渲染确认卡片（摘要 + 确认/取消两个按钮 + 倒计时），点击后调 §1.3 的接口 |
| 聊天组件 | 页面加载时调 `GET /ai/chat/pending-action/list?status=PENDING` 恢复未处理的卡片 |
| 知识库页 | 向量库状态卡片按 §2.3 的新字段改；重建按钮加一个"同时清空旧向量"的勾选（对应 `truncate`） |
| 指标页 | 新增 4 个指标卡片；`ragHitRate` 旁标注口径 |
| 评测页（可选） | 一个表格 + 一个"跑评测"按钮就够，不必做图表 |

> 前端改动**刻意压到最小**：`intent` 和 `pending_action` 是必须做的（一个改善体验、一个是安全闭环），其余都是文案和字段级调整。这次改造的价值在后端，不要在前端上花时间。
