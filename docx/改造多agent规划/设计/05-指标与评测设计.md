# 05 · 指标与评测设计（在线监测 + 离线黄金集）

> 两套数据，用途不同，别混：**在线指标**回答"系统现在是好是坏"，**离线黄金集**回答"这次改动到底有没有用"。
> 所有 SQL 对照现有表结构（`ai_chat_turn_audit` / `ai_tool_call_log` / `ai_chat_message` / `ai_chat_session`）写成，迁移脚本全部用 `information_schema` 动态判断，可反复执行。

## 一、在线指标

### 1.1 清单

| 指标 | 数据来源 | 含义 | 预警线 |
|------|---------|------|--------|
| 工具调用成功率 | `ai_tool_call_log.success_flag` | 工具执行成功占比 | < 90% |
| RAG 命中率 | `ai_chat_turn_audit.has_rag_hit`，**分母限定 `rag_enabled=1`** | 挂了 RAG 的轮次里，真正检索到东西的比例 | < 40% |
| 满意度 | `ai_chat_message.feedback` | 赞 ÷ (赞+踩) | 看趋势 |
| 转人工率 | `ai_tool_call_log.tool_name='escalateToHuman'` | 按会话去重计算 | > 12% |
| 平均轮数 | `ai_chat_message` 按 session 聚合 | 对话复杂度 | 突然升高 = 路由或上下文变差 |
| **失败率** `[新增]` | `failure_count > 0` 的轮次占比 | 重试耗尽、用户看到"系统繁忙"的比例 | > 5% |
| **重试率** `[新增]` | `retry_count > 0` 的轮次占比 | 触发过重试的比例 | > 10% |
| **超时率** `[新增]` | `is_timeout = 1` 的轮次占比 | 模型端卡住的比例 | > 3% |
| **p95 延迟** `[新增]` | `duration_ms` 的 95 分位 | 用户实际等待 | 看趋势，改造后不应变差 |
| **规则路由覆盖率** `[新增]` | `route_source = 'rule'` 的轮次占比 | 有多少轮**完全没花**路由模型调用 | 越高越好 |

新增这 5 个的动机很直接：审计表里出现过连续多条"抱歉，系统暂时繁忙"，但**现有指标一个都反映不出来**。不量化它，就无从判断重试参数、超时时间、规则路由这些改动到底有没有效果。

**改造前的实测基线**（`ai_chat_turn_audit` 全部 82 轮，改造前先把这几个数抄下来，否则后面没法说"改善了多少"）：

| 指标 | 改造前实测 |
|------|-----------|
| 失败率 | **6.1%**（5 / 82 轮回复是"系统暂时繁忙"） |
| 耗时中位数 | **10.7 秒** |
| **p95 延迟** | **约 29 秒** |
| 最慢一轮 | **96.9 秒** |
| 超时率 | 量不到（`is_timeout` 字段还不存在，且底层没有读超时，02 §9.1） |

> 失败率 6.1% 已经超过上面自己定的 5% 预警线；p95 29 秒对一个客服对话来说也偏高。**这两个数字是整套改造的起点，也是最好用的面试素材**——"我不是觉得多智能体时髦才改的，是审计表里 82 轮有 5 轮直接失败、p95 29 秒。"

### 1.2 一个必须显式处理的口径变化

改造后 `order-service` 和 `account` 两个域不挂 RAG（02 §四）。如果 `ragHitRate` 还按"全部轮次"当分母，这两个域的轮次会白白拉低命中率——**那是口径造成的假下降，不是效果退化**。

处理办法：审计表加 `rag_enabled` 字段，命中率只在 `rag_enabled = 1` 的行上算，接口里带上 `ragHitRateScope` 字段标明口径（04 §3.1）。

> 面试话术："改造后 RAG 命中率的分母变了，因为两个域我故意不挂 RAG。所以我在审计表加了 `rag_enabled`，指标只在这个字段为 1 的行上算，改造前后才是同口径。这种事不显式处理，最后就会拿着一个自己造出来的'下降'去解释半天。"

## 二、指标 SQL（照 `DashboardController` 现有写法补进 `getAiMetrics`）

现有代码里每个指标都是"一段 SQL + 一个 try/catch 兜 0"，新增的 4 个照同样结构写，时间条件继续用 `withinDaysCondition("create_time", days)`。

```sql
-- 失败率 / 重试率 / 超时率：一条 SQL 出三个值，少两次往返
SELECT ROUND(SUM(CASE WHEN failure_count > 0 THEN 1 ELSE 0 END) * 100.0 / NULLIF(COUNT(*), 0), 1) AS failureRate,
       ROUND(SUM(CASE WHEN retry_count   > 0 THEN 1 ELSE 0 END) * 100.0 / NULLIF(COUNT(*), 0), 1) AS retryRate,
       ROUND(SUM(CASE WHEN is_timeout    = 1 THEN 1 ELSE 0 END) * 100.0 / NULLIF(COUNT(*), 0), 1) AS timeoutRate
  FROM ai_chat_turn_audit
 WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
   AND user_id <> -1;      -- 排除离线评测流量，取值与理由见 §6.3
```

```sql
-- p95 延迟：MySQL 8 没有 percentile 函数，用窗口函数取 95 分位
SELECT ROUND(MAX(duration_ms)) AS p95Latency
  FROM (
        SELECT duration_ms,
               PERCENT_RANK() OVER (ORDER BY duration_ms) AS pr
          FROM ai_chat_turn_audit
         WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
           AND user_id <> -1
           AND duration_ms IS NOT NULL
       ) t
 WHERE pr <= 0.95;
```

```sql
-- RAG 命中率（新口径）：分母只算挂了 RAG 的轮次
SELECT ROUND(SUM(CASE WHEN has_rag_hit = 1 THEN 1 ELSE 0 END) * 100.0 / NULLIF(COUNT(*), 0), 1) AS ragHitRate
  FROM ai_chat_turn_audit
 WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
   AND user_id <> -1
   AND rag_enabled = 1;
```

```sql
-- 规则路由覆盖率 + 各意图分布：这张表决定"要不要继续往规则表里加关键词"
SELECT route_source,
       intent,
       COUNT(*) AS cnt,
       ROUND(AVG(duration_ms)) AS avgMs
  FROM ai_chat_turn_audit
 WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
   AND user_id <> -1
 GROUP BY route_source, intent
 ORDER BY cnt DESC;
```

> ⚠️ 现有代码是把 `days` 直接拼进 SQL 字符串的（`withinDaysCondition`）。它安全的前提是 `normalizeDays()` 已经把入参夹在 1~90 的整数区间内。**新增 SQL 要么继续用这个已经夹过的值，要么用占位符绑定，别自己开一条新的拼接路径。**

## 四、离线黄金集

### 4.1 它解决在线指标解决不了的问题

在线指标有个根本局限：**每天面对的问题不一样**。今天用户问的偏简单，命中率就高；明天来一批冷门问题，命中率就掉。拿它判断"块大小从 800 改到 500 有没有用"，等于在移动的靶子上打枪。

黄金集把靶子固定住：同一批问题、同一份标注、只改一个参数，两次跑出来的差值才是那个参数的效果。

### 4.2 K 必须定死，不能跟着 `final-top-k` 走

这是最容易犯、也最容易自欺的错误：

> 把 `final-top-k` 从 4 调到 8，然后欣喜地发现 Recall 从 55% 涨到 71%。

Recall 当然涨——你多看了 4 个候选。这不是链路变好了，是**评测口径变松了**。

所以：

- 评测的 K 用独立配置项 `smart-cs.eval.k`，**定死在 8**，任何参数实验都不许动它；
- 同时另报一个 `Recall@final-top-k`，反映"真正喂给模型的那几块里召回了多少"。

前者衡量检索链路的能力上限，后者衡量当前配置的实际效果，两个数字都要看。只看后者会把"调大 topK"误当成优化。

### 4.3 ground truth 标到「知识条目」，不标到「块」

`ai_eval_golden.truth_chunk_ids` 这个列名是历史遗留，**里面存的是条目级前缀**，例如 `["knowledge_33","knowledge_41"]`，而不是 `knowledge_33_c2`。

理由很硬：块 id 的格式是 `knowledge_{id}_c{chunkIndex}`（01 §6.1），`chunkIndex` 由分块参数决定。块大小从 800 改到 500，`knowledge_33` 从 2 块变 4 块，你标的 `knowledge_33_c2` 指向的内容完全变了——**整份标注当场作废**。而调块大小恰恰是最需要黄金集来验证的动作之一。

标到条目级，分块参数怎么改都不影响标注有效性。匹配时把块 id 的 `_c{n}` 后缀去掉再比：

```java
/** knowledge_33_c2 → knowledge_33 ；doc_7_c12 → doc_7 */
static String entryKey(String chunkId) {
    return chunkId == null ? "" : chunkId.replaceFirst("_c\\d+$", "");
}
```

代价是 Precision 的口径偏松：同一条目的所有块都算相关，哪怕只有一块真含答案。这个偏差是**系统性的**——同一份标注、同一套代码，改造前后都往同一个方向偏，所以**做相对比较没问题，但别把这个 Precision 值当绝对水平去汇报**。

### 4.4 黄金集从哪来：先看存量，再定规模

凭空编的 100 个问题全是"标准问法"，而真实提问是"这个能不能退啊""昨天买的那个多久到"。用编的问题调出来的参数，上线不生效。

```sql
-- 优先挑「没命中 RAG 但本该命中」和「失败过」的真实提问
SELECT user_message, intent, has_rag_hit, failure_count, COUNT(*) AS freq
  FROM ai_chat_turn_audit
 WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL 30 DAY)
   AND CHAR_LENGTH(user_message) BETWEEN 4 AND 80
 GROUP BY user_message, intent, has_rag_hit, failure_count
 ORDER BY (failure_count > 0) DESC, has_rag_hit ASC, freq DESC
 LIMIT 200;
```

> ⚠️ **先认清现有存量，别按 200 条去规划。** 查过真实数据：`ai_chat_turn_audit` 现在总共 **82 行**，去掉"你好""1""2"这类无效提问后能用的**不到 40 条**；`ai_knowledge` 只有 **29 条**，其中 `PRODUCT_INFO` 24 / `FAQ` 3 / `POLICY` 2 / `GUIDE` 0。
> 直接后果是：**下面那张 100 条的分布表现在凑不出来**——`POLICY` 想要 30 条问题，可对应的知识只有 2 条；`GUIDE` 想要 20 条，对应知识 0 条。硬凑出来的黄金集，Recall\@8 会虚高到没有区分度（候选池比 K 大不了多少），调参根本看不出差异。
>
> 所以顺序要反过来，分两步：
> 1. **先补知识库**。`POLICY` 补到 15~20 条（退换货、保修、运费、发票、隐私各拆成独立条目），`GUIDE` 补到 10 条左右（下单、支付、申请售后、改地址的操作步骤）。这一步是**内容工作，不是代码工作**，但它是评测能不能算数的前提。
> 2. **再建黄金集**。存量真实提问先全部用上（约 30~40 条，这批最有价值），不够的部分照着知识条目反向出题，并在 `ai_eval_golden.remark` 里标清楚哪些是真实提问、哪些是补写的。
>
> 起步阶段先按 **40~50 条**跑基线（07 §1.3 建议的 30 条同理），比硬凑 100 条更诚实。面试被问到规模时，"我用了 45 条，其中 32 条来自线上真实提问"比"我做了 100 条"更经得起追问。

从上面这批候选里筛条目，分布别平均，按"改造后要证明什么"来配（下表是知识库补全后的目标配比，**列的是比例而不是死数字**）：

| 类别 | 占比 | 用来证明什么 |
|------|------|-------------|
| `POLICY` 政策条款（退货几天、保修范围） | 30% | 检索主战场，Recall/MRR 的主要来源 |
| `PRODUCT_INFO` 商品参数与型号 | 25% | 其中至少 1/3 **必须含型号/SKU**（如 `RK87`），专门验证 P5 全文路 |
| `GUIDE` 操作指引 | 20% | 多步骤长文本，验证块大小与父块补全 |
| `FAQ` 常见问题（支付方式、发货时效） | 5% | 现有 3 条 `FAQ` 的回归护栏——防止类别过滤把它们漏掉（02 §四） |
| 路由类（问订单/改地址/闲聊/转人工） | 15% | 只评 Intent Accuracy，不标 chunk |
| 跨域（一句话两件事） | 5% | 验证 `CROSS_DOMAIN` 规则不误判 |

> 路由类那 20 条 `truth_chunk_ids` 留空。`order-service` / `account` 本来就不挂 RAG（02 §四），给它们标 chunk 毫无意义，还会把 Recall 的分母污染成"含永远召不回来的用例"。**检索指标的分母里只放挂了 RAG 的用例**——和在线 `rag_enabled=1` 是同一个道理。

## 五、指标定义

`K = smart-cs.eval.k`（= 8）。相关性判定 = 块的 `entryKey` 落在 `truth_chunk_ids` 里。

| 指标 | 算法 | 回答什么 | 分母范围 |
|------|------|---------|---------|
| **Recall@K** | 命中的相关条目数 ÷ 标注的相关条目数 | 该找到的找回来了多少 | 有标注且挂 RAG 的用例 |
| **Precision@K** | top-K 里属于相关条目的块数 ÷ 实际返回块数 | 喂给模型的内容有多少有用 | 同上 |
| **MRR** | 第一个相关块的排名倒数，逐条平均 | 有用的排得够不够前 | 同上 |
| **Hit Rate@K** | top-K 里至少命中一个的用例占比 | 彻底没召回的用例有多少 | 同上 |
| **Intent Accuracy** | 路由结果 == `expect_intent` 的占比 | 路由判对了多少 | 标了 `expect_intent` 的用例 |
| **Tool Accuracy** | `expect_tools` 被完全覆盖的用例占比 | Worker 选对工具了吗 | 标了 `expect_tools` 的用例 |
| **Faithfulness** | judge 的 0~5 分归一到百分制 | 回答是否被检索到的资料支持 | 实际跑了 Worker 的用例 |

四个口径细节，不写清以后自己会算错：

1. **Precision 的分母用"实际返回条数"而不是 K。** 候选不足 K 条时（阈值偏高或类别过滤严），拿 K 当分母会凭空压低 Precision，看着像"检索变差"，其实是"返回变少"。
2. **MRR 用块级排名，不是条目级。** 用户体感取决于第一条有用资料排在第几位，那就是块的位置。
3. **Recall 逐条算再平均（macro），不是把所有命中数加起来除以所有标注数（micro）。** macro 让每条用例权重相同，标了 3 个条目的难题不会主导整个指标。
4. **Tool Accuracy 用"覆盖"而不是"完全相等"。** 模型多调一次 `getProductDetail` 去核对信息不算错；该调的没调才算错。多调的问题由在线工具预算指标（02 §十）管。

### 5.1 Faithfulness 的两个局限（主动说，别等人问）

**judge 和 Worker 默认是同一个型号**（02 §三 三个模型默认值相同），同族模型给自己打分偏高，这叫自我偏好偏差。缓解办法：judge 只做"要点覆盖 + 是否有资料支持"这类接近二元的判断，不评文风；`smart-cs.model.judge` 是独立配置项，想换异构模型随时能换。

**judge 打分不可复现**，同一份输入跑两次可能差 0.2 分。所以 Faithfulness **只看大幅变化**，小波动一律当噪声。检索指标则是确定性的——同一份向量数据、同一个 query，结果一模一样，这些才可以拿来比几个百分点的差异。

## 六、评测管道实现

### 6.1 前提：把检索抽成一层，线上与评测共用

03 §五 把检索融合写在 `HybridRagAdvisor.before()` 里。评测**必须走线上同一条路**，否则评的是另一份代码。所以要做一个小重构——把"两路召回 → RRF → 重排 → 截断"抽成独立组件，Advisor 和评测都调它：

```java
/** 线上对话与离线评测共用的唯一检索入口 */
public interface RagRetrievalService {
    /** categories 为空表示不过滤；topK 为最终返回条数 */
    List<ScoredDoc> retrieve(String query, List<String> categories, int topK);
}
```

`HybridRagAdvisor` 改成调 `retrieve(query, cats, props.getRag().getFinalTopK())`，`EvaluationJob` 调 `retrieve(query, cats, props.getEval().getK())`。默认实现叫 `HybridRagRetrievalService`（装的就是原来 `before()` 里那段逻辑）。如果评测自己写一份检索逻辑，**跑出来的数字再漂亮也和线上无关**。

### 6.2 分层执行：检索/路由默认跑，工具/忠实度默认不跑

```yaml
smart-cs:
  eval:
    dataset: v1
    k: 8                  # 评测口径，定死不动
    run-agent: false      # 是否真的跑 Worker（评 Tool Accuracy / Faithfulness）
    judge-enabled: false  # 是否让 judge 打忠实度分
    user-id: -1           # 评测专用 userId，在线指标一律排除
    legacy-retrieval: false   # true = 用改造前的检索实现跑基线（§7.1）
```

| 层 | 评什么 | 成本 | 副作用 |
|----|--------|------|--------|
| 检索层（直调 `RagRetrievalService`） | Recall / Precision / MRR / Hit Rate | 每条 1 次 embedding | 无，不写任何业务表 |
| 路由层（直调 `IntentRouter.route`） | Intent Accuracy | 规则命中为 0，仅兜底时 1 次模型调用 | 无 |
| Worker 层（`run-agent: true`） | Tool Accuracy / Faithfulness | 每条 1~N 次模型调用 + 真实工具执行 | **会真的执行工具、会写审计表** |

前两层随便跑，改一个参数跑一次，几十秒出结果。第三层花钱且有副作用，默认关。这也解释了 `ai_eval_result` 里 `tool_accuracy` / `faithfulness` 为什么允许为 NULL——**没跑就是 NULL，绝不能填 0**，填 0 会在趋势图上变成一次假的"暴跌"。

### 6.3 跑 Worker 时的两条硬约束

**一、黄金集里只允许只读工具。** `cancelOrder` / `payOrder` / `checkoutFromCart` / `clearCart` 这类写操作**不能出现在 `expect_tools` 里**。评测是要反复跑的，每跑一次就真取消一批订单——那不是评测，是事故。校验放在入库时：

```java
private static final Set<String> FORBIDDEN_IN_GOLDEN =
        Set.of("cancelOrder", "payOrder", "checkoutFromCart", "clearCart",
               "submitTicket", "updateAddress", "deleteAddress", "addToCart");

void validate(EvalGolden g) {
    List<String> tools = readJsonList(g.getExpectTools());
    for (String t : tools) {
        if (FORBIDDEN_IN_GOLDEN.contains(t)) {
            throw new ServiceException("黄金集不允许写操作工具: " + t);
        }
    }
}
```

> 这份名单和 `smart-cs.agent.hitl-tools`（02 §十三）重叠但**不能直接复用**：HITL 名单是"需要用户确认的"，这份是"评测绝对不能碰的"，后者必须更宽。`updateAddress` 没危险到需要确认，但评测跑 50 次就把地址改 50 次。

**二、评测流量必须能从在线指标里剔除。** 跑 Worker 会写 `ai_chat_turn_audit`、`ai_tool_call_log`、`ai_chat_message`，100 条评测数据混进当天在线指标，失败率和延迟全被污染。用固定的 `smart-cs.eval.user-id`（取负数，不可能是真实用户 id）来标记，然后分两种情况排除：

`ai_chat_turn_audit` 有 `user_id`，直接过滤（§二 的四条 SQL 都已经带上）：

```sql
   AND user_id <> -1        -- 值取自 smart-cs.eval.user-id
```

`ai_tool_call_log` 和 `ai_chat_message` **只有 `session_id`，没有 `user_id`**（读实体类确认的）。这两张表上的指标——工具成功率、满意度、转人工率——必须绕 `ai_chat_session` 排除：

```sql
-- 工具调用成功率（改造后口径）：评测会话的工具调用不算进线上成功率
SELECT ROUND(SUM(CASE WHEN t.success_flag = 1 THEN 1 ELSE 0 END) * 100.0
             / NULLIF(COUNT(*), 0), 1) AS toolSuccessRate
  FROM ai_tool_call_log t
  JOIN ai_chat_session s ON s.session_id = t.session_id
 WHERE t.create_time >= DATE_SUB(CURDATE(), INTERVAL ? DAY)
   AND s.user_id <> -1;
```

> 这是三张表里最容易漏的一处：只给审计表加了排除、忘了工具日志，结果就是"工具成功率突然掉了 8 个点"——因为评测跑的都是最难的用例。改造前后的在线对比要能看，这三张表的口径必须一起改。
>
> 另一种更省事的做法是让评测**不复用会话表**（不建 `ai_chat_session` 记录），但那会让 Worker 层的记忆 Advisor 拿不到会话上下文，跑出来的行为和线上不一致。宁可多写三个 `JOIN`。

### 6.4 `EvaluationJob` 主流程

```java
/** 一条用例（从 ai_eval_golden 读出后转成的内存形态） */
public record GoldenCase(Long goldenId, String question, String expectIntent,
                         List<String> expectTools, List<String> truthKeys,
                         String answerPoints, String category) {}

/** 一次评测的汇总。可为空的三项：没跑就是 null，不是 0 */
public record EvalMetrics(int caseCount, Double recallAtK, Double recallAtFinalK,
                          Double precisionAtK, Double mrr, Double hitRate,
                          Double intentAccuracy, Double toolAccuracy,
                          Double faithfulness, long avgDurationMs) {}
```

```java
@Service
@RequiredArgsConstructor
public class EvaluationJob {

    private static final Logger log = LoggerFactory.getLogger(EvaluationJob.class);

    private final EvalGoldenMapper goldenMapper;
    private final EvalResultMapper resultMapper;
    private final RagRetrievalService retrieval;      // 与线上同一条检索路径（§6.1）
    private final IntentRouter router;
    private final SmartCsProperties props;
    private final ObjectMapper objectMapper;

    public EvalMetrics run(String dataset, String remark) {
        List<GoldenCase> cases = loadCases(dataset);
        if (cases.isEmpty()) {
            throw new ServiceException("黄金集为空或全部停用: " + dataset);
        }
        int k = props.getEval().getK();
        Acc acc = new Acc();
        long t0 = System.currentTimeMillis();

        for (GoldenCase c : cases) {
            try {
                evalOne(c, k, acc);
            } catch (Exception e) {
                // 单条失败绝不能中断整轮，否则 99 条白跑
                acc.errorCount++;
                log.warn("评测单条失败 - goldenId: {}, err: {}", c.goldenId(), e.getMessage());
            }
        }
        long avgMs = (System.currentTimeMillis() - t0) / cases.size();
        EvalMetrics m = acc.summarize(cases.size(), avgMs);
        save(dataset, m, remark);
        log.info("评测完成 - dataset: {}, 用例: {}, 异常: {}, 结果: {}",
                dataset, cases.size(), acc.errorCount, m);
        return m;
    }

    private void evalOne(GoldenCase c, int k, Acc acc) {
        // ① 路由层：规则命中零成本
        IntentRouter.RouteDecision d = router.route(c.question());
        if (StringUtils.isNotEmpty(c.expectIntent())) {
            acc.intentTotal++;
            if (c.expectIntent().equals(d.intent().name())) acc.intentHit++;
        }

        // ② 检索层：类别过滤用「期望意图」而不是「路由实际结果」
        Intent forRag = intentForRag(c, d);
        if (!c.truthKeys().isEmpty() && !forRag.ragCategories.isEmpty()) {
            List<ScoredDoc> docs = retrieval.retrieve(c.question(), forRag.ragCategories, k);
            acc.addRetrieval(c.truthKeys(), docs, props.getRag().getFinalTopK());
        }

        // ③ Worker 层：默认关，开了才跑（§6.3 两条硬约束）
        if (props.getEval().isRunAgent()) {
            runAgentAndScore(c, acc);
        }
    }

    /** 有 expect_intent 就用它，没标才退回路由结果 */
    private Intent intentForRag(GoldenCase c, IntentRouter.RouteDecision d) {
        if (StringUtils.isEmpty(c.expectIntent())) return d.intent();
        try {
            return Intent.valueOf(c.expectIntent());
        } catch (IllegalArgumentException e) {
            log.warn("黄金集 expect_intent 不是合法枚举 - goldenId: {}, value: {}",
                    c.goldenId(), c.expectIntent());
            return d.intent();
        }
    }
}
```

第 ② 步用**期望意图**而不是路由结果，是有意的：如果用路由结果，路由错一条，检索指标跟着掉，两个数字纠缠在一起——改完参数你分不清是路由的功劳还是检索的功劳。分开算之后，Intent Accuracy 管路由、Recall 管检索，各自独立归因。

> `Intent.valueOf` 会对脏数据抛异常，这里兜住并降级，但**根治点在入库校验**：新增黄金集条目时就把 `expect_intent` 校验成合法枚举值（和 §6.3 的工具名校验放在一起）。

### 6.5 累加器：所有除法只在最后做一次

```java
    /** 逐条攒分，summarize 时才算平均。entryKey 见 §4.3 */
    private static class Acc {
        int ragTotal, hitCount, intentTotal, intentHit, toolTotal, toolHit, faithCount, errorCount;
        double recallSum, recallFinalSum, precisionSum, rrSum, faithSum;

        /** docs 是按相关性降序的 top-K；Recall@final-top-k 直接取前缀，不用再查一次 */
        void addRetrieval(List<String> truthKeys, List<ScoredDoc> docs, int finalTopK) {
            ragTotal++;
            Set<String> truth = new HashSet<>(truthKeys);
            Set<String> hitEntries = new HashSet<>();
            Set<String> hitEntriesInFinal = new HashSet<>();
            int relevantChunks = 0;
            int firstRelevantRank = 0;

            for (int i = 0; i < docs.size(); i++) {
                String key = entryKey(docs.get(i).id());
                if (!truth.contains(key)) continue;
                relevantChunks++;
                hitEntries.add(key);
                if (i < finalTopK) hitEntriesInFinal.add(key);
                if (firstRelevantRank == 0) firstRelevantRank = i + 1;
            }

            recallSum      += (double) hitEntries.size() / truth.size();
            recallFinalSum += (double) hitEntriesInFinal.size() / truth.size();
            // 分母是「实际返回条数」而不是 K（§五 细节 1）
            precisionSum   += docs.isEmpty() ? 0d : (double) relevantChunks / docs.size();
            rrSum          += firstRelevantRank == 0 ? 0d : 1d / firstRelevantRank;
            if (firstRelevantRank > 0) hitCount++;
        }

        /** 覆盖即算对：该调的都调了就行，多调不算错（§五 细节 4） */
        void addTools(List<String> expect, List<String> actual) {
            if (expect == null || expect.isEmpty()) return;
            toolTotal++;
            if (new HashSet<>(actual).containsAll(expect)) toolHit++;
        }

        void addFaithfulness(double score0to5) {
            faithCount++;
            faithSum += score0to5;
        }

        EvalMetrics summarize(int caseCount, long avgMs) {
            return new EvalMetrics(caseCount,
                    pct(recallSum, ragTotal),
                    pct(recallFinalSum, ragTotal),
                    pct(precisionSum, ragTotal),
                    pct(rrSum, ragTotal),
                    pct(hitCount, ragTotal),
                    pct(intentHit, intentTotal),
                    pct(toolHit, toolTotal),
                    pct(faithSum / 5d, faithCount),        // 0~5 分归一到百分制
                    avgMs);
        }

        /** 分母为 0 返回 null：含义是「这次没评这一项」，不是「得了 0 分」 */
        private static Double pct(double num, int den) {
            return den == 0 ? null
                    : BigDecimal.valueOf(num * 100d / den)
                            .setScale(2, RoundingMode.HALF_UP).doubleValue();
        }
    }
```

`ragTotal` 是**检索指标自己的分母**，只在真正跑了检索的用例上累加。它和 `caseCount`（100）不相等，路由类那 20 条不进这个分母——这就是 §4.4 说的"分母里只放挂了 RAG 的用例"在代码里的落点。

### 6.7 接口：一把 Redis 锁 + 必须放在 `finally` 的释放

```java
@RestController
@RequestMapping("/ai/eval")
@RequiredArgsConstructor
public class EvalController extends BaseController {

    private static final String LOCK_KEY = "ai:eval:running";

    /** RedisCache 没有 setIfAbsent，这里直接用 template；bean 类型是 RedisTemplate<Object,Object> */
    private final RedisTemplate<Object, Object> redisTemplate;
    private final EvaluationJob job;

    @PreAuthorize("@ss.hasPermi('ai:eval:run')")
    @PostMapping("/run")
    public AjaxResult run(@RequestParam(defaultValue = "v1") String dataset,
                          @RequestParam(required = false) String remark) {
        Boolean got = redisTemplate.opsForValue()
                .setIfAbsent(LOCK_KEY, System.currentTimeMillis(), 30, TimeUnit.MINUTES);
        if (!Boolean.TRUE.equals(got)) {
            return AjaxResult.error("已有评测任务在跑，等它结束再点");
        }
        try {
            return AjaxResult.success(job.run(dataset, remark));
        } finally {
            redisTemplate.delete(LOCK_KEY);   // 不放 finally，一次异常就锁死 30 分钟
        }
    }
}
```

> 用 `setIfAbsent` 而不是"`hasKey` 判断再 `setCacheObject`"：后者是两步操作，两个人同时点就都能进去。30 分钟过期只是**进程被 kill 时的兜底**，正常释放靠 `finally`。
>
> ⚠️ 这是长耗时同步接口。只跑检索层，100 条大约几十秒，Nginx 默认的 60s `proxy_read_timeout` 勉强够用；一旦开 `run-agent`，耗时会到几分钟，**必须先把 06 §3.2 的 `nginx.conf` 里 `proxy_read_timeout` 调大**，否则前端拿到 504、后端还在跑、锁还占着，界面上看起来就是"评测坏了"。

## 七、基线与同集对比

### 7.1 基线怎么跑：同一个接口，两个实现

"改造前"的检索是 `SimpleVectorStore` + topK=3 + threshold=0.5，`RagRetrievalService` 那时还不存在。做法是给这个接口先写一个**临时实现**，P1 之前就把基线跑出来：

```java
/** 只在跑基线时存在，P2 上线后删掉。直接查向量库，无类别过滤、无融合、无重排 */
@Service
@ConditionalOnProperty(name = "smart-cs.eval.legacy-retrieval", havingValue = "true")
@RequiredArgsConstructor
public class LegacyRetrievalService implements RagRetrievalService {

    private final VectorStore vectorStore;

    @Override
    public List<ScoredDoc> retrieve(String query, List<String> categories, int topK) {
        // 注意：topK 用评测口径（8），不用线上那个 3；categories 故意忽略——改造前就没有过滤
        List<Document> docs = vectorStore.similaritySearch(SearchRequest.builder()
                .query(query).topK(topK).similarityThreshold(0.5).build());
        return docs == null ? List.of() : docs.stream()
                .map(d -> new ScoredDoc(d.getId(), d.getText(), d.getMetadata(),
                        d.getScore() == null ? 0d : d.getScore()))
                .toList();
    }
}
```

> `topK` 用 8 而不是现状线上的 3：线上 topK 是**配置**，评测 K 是**口径**（§4.2）。基线用 3、改造后用 8，比出来的差值一半来自口径，那样的对比没有意义。
>
> ⚠️ 两个实现必须互斥，否则容器里有两个 `RagRetrievalService` 会启动失败。`HybridRagRetrievalService` 上加反向条件：
> `@ConditionalOnProperty(name = "smart-cs.eval.legacy-retrieval", havingValue = "false", matchIfMissing = true)`

这里有个恰好成立的好事：现状代码的 document id 是 `"knowledge_" + knowledgeId`（没分块，一条知识一个 Document），改造后是 `knowledge_{id}_c{n}`。`entryKey()` 去掉 `_c{n}` 后缀之后，**两边算出来的 key 完全一样**。所以条目级标注不用为基线做任何特殊处理——这也是 §4.3 那个决定的第二个好处。

### 7.3 四条纪律

**一次只改一个参数。** 同时改了块大小和 topK，结果变好了，你不知道该保留哪个改动，下次退回去也不知道退哪个。

**`remark` 必填。** 写"P5 全文路开启后"，不要写"试一下"。这一列是 `config_snapshot` 的自然语言索引。

**认清噪声区间。** 100 条用例，Recall 是逐条平均，**一条用例从全错到全对 ≈ 1 个百分点**。所以：

| 指标 | 视为噪声 | 视为有效变化 |
|------|---------|-------------|
| Recall / Precision / MRR / Hit Rate（确定性） | < 3pp | ≥ 3pp |
| Faithfulness（judge 打分，不可复现） | < 10pp | ≥ 10pp |

拿着 +1.5pp 说"优化有效"，是这套体系最容易出现的自欺。

**跨口径的数字不许并排放。** 三种情况下两列不可比：换了 `dataset`（靶子换了）、改了 `eval.k`（尺子换了）、分块口径变了（Precision 是块级指标，不分块 vs 分块之间不可比，**但条目级的 Recall 仍然可比**）。前两种直接不要比；第三种把 Precision 那一格留空，只比 Recall/MRR。

## 八、调优决策树

指标不是用来汇报的，是用来决定"下一步改哪里"的。按这棵树走，不要凭手感调参。

```
① Hit Rate@8 < 70%（大量用例一条相关的都没召回）
   ├─ 先查标注对应的知识条目在库里吗
   │    SELECT knowledge_id, title, status FROM ai_knowledge WHERE knowledge_id IN (...);
   │    └─ 不在 / status=0 → 不是检索问题，是知识库缺内容。补内容，别调参数。
   └─ 在库里却召不回
        ├─ 精确词（型号 RK87 / SKU / 单号）召不回  → 开 full-text-enabled（P5，03 §4.3）
        ├─ 口语化提问召不回                        → similarity-threshold 0.4 → 0.35
        └─ 只有某个类别的用例召不回                → 查这些条目的 metadata.category 标对了没
                                                    （类别过滤误伤是最隐蔽的一种失败）

② Hit Rate 高（>85%）但 Recall@8 中等
   └─ 一条用例标了多个相关条目，只召回了一部分 → 提 vector-top-k / fusion-top-k

③ Recall@8 高（>80%）但 MRR / Precision 低
   └─ 该找到的都找到了，只是没排在前面 → 这是重排收益最大的情形，开 rerank（03 §6.2）
      反之若 Recall 本身就低，先做 ①，重排救不回没召回的块

④ Recall@8 明显高于 Recall@final-top-k
   └─ 候选里有、但没进最终喂给模型的那几块 → 提 final-top-k 或开 rerank
      （只提 final-top-k 要盯住 token 与延迟，别为 +2pp 付 30% 的 prompt 长度）

⑤ Faithfulness 低但 Recall 高（资料给到了，回答没用好）
   ├─ 回答没引用检索到的内容 → Worker Prompt 问题（02 §六）
   ├─ 块被切碎、上下文断了   → 试 parent-expand: true（03 §7.2），开关各跑一次看是否一起涨
   └─ 回答里有资料里没有的内容 → "不确定就说不知道"那条约束没生效，加强 Prompt

⑥ Intent Accuracy < 90%
   └─ 先看审计表里 route_source 的分布，判断错的是规则还是模型
        SELECT route_source, intent, COUNT(*) FROM ai_chat_turn_audit ... GROUP BY 1,2;
        ├─ rule 错 → 关键词冲突。DOMAIN_RULES 的顺序就是优先级（02 §8.2），先调顺序再加词
        └─ llm  错 → 路由 Prompt 里意图描述区分度不够；高频错法直接加进规则表兜住

⑦ Tool Accuracy < 85%
   ├─ 该调的工具没调  → @Tool 的 description 不像用户的说法，照真实提问改写
   └─ 调了别的域的工具 → 这是路由错了，先看 ⑥，别动工具
```

> 整棵树只有一个前提：**每次只走一个分支，改完立刻重跑同一份黄金集**。同时动两处，指标涨了也说不清是谁涨的。

## 九、三套数据的分工与闭环

开头说"两套数据"，严格讲是三套：在线抽检（02 §十二 的 `Evaluator`）介于两者之间。

| | 在线指标 | 在线抽检 | 离线黄金集 |
|---|---------|---------|-----------|
| 回答什么 | 系统现在是好是坏 | 哪一轮答得不好 | 这次改动有没有用 |
| 数据 | 全量真实流量 | 10% 采样真实流量 | 固定 100 条 |
| 有 ground truth | 没有 | 没有（judge 主观判断） | 有（人工标注） |
| 能定位到具体一轮 | 不能 | 能 | 不适用 |
| 落在哪 | Dashboard | `ai_chat_turn_audit.eval_score` | `ai_eval_result` |
| 主要用途 | 预警 | 挖 bad case | 归因与决策 |

闭环在这里：**抽检打出低分的轮次 → 人工看一眼 → 值得的补进黄金集 → 下次评测就能量化**。黄金集是这样从 30 条长到 100 条的，不是一次编 100 条编出来的。

```sql
-- 每周挖一次 bad case，人工筛完补进 ai_eval_golden
SELECT audit_id, user_message, LEFT(ai_response, 80) AS answer_head,
       eval_score, eval_reason, intent, agent_id
  FROM ai_chat_turn_audit
 WHERE eval_score IS NOT NULL
   AND eval_score <= 2
   AND create_time >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)
 ORDER BY eval_score ASC, create_time DESC
 LIMIT 50;
```

## 十一、风险与规避

| 风险 | 表现 | 规避 |
|------|------|------|
| 评测写了第二份检索实现 | 指标漂亮，线上没改善 | 单一入口 `RagRetrievalService`（§6.1） |
| K 跟着 `final-top-k` 变 | 调大 topK 被当成优化成果 | `eval.k` 定死 + 另报 `Recall@final-top-k`（§4.2） |
| ground truth 标到块 id | 一改分块参数，整份标注作废 | 条目级前缀 + `entryKey`（§4.3） |
| 评测流量污染在线指标 | 工具成功率无故掉几个点 | `eval.user-id`；工具日志与消息表没有 `user_id`，要 `JOIN` 会话表排除（§6.3） |
| 黄金集含写操作工具 | 每跑一次评测就改一批真实数据 | 入库黑名单校验（§6.3） |
| 拿 ±1pp 当结论 | 一路"优化"，最终没变好 | 噪声区间表（§7.3） |
| judge 自评偏高 | Faithfulness 虚高 | judge 模型可换 + 只认 ≥10pp 的变化（§5.1） |
| 未跑的指标落 0 | 趋势图上出现假暴跌 | 没跑就是 NULL（§6.2） |
| 迁移脚本不幂等 | 换环境执行中断 | `information_schema` 动态判断（§3.1） |
| 快照缺关键参数 | 结果无法复现 | `chunk-size` 先外置成配置项（§6.6、03 §八） |
| 长耗时接口超时 | 前端 504，锁还占着 | 调大 `proxy_read_timeout` + `finally` 释放锁（§6.7） |

## 十二、面试会追问的三个点

**"你怎么证明 RAG 优化是有效的，而不是自我感觉？"**
固定 100 条黄金集，标注标在知识条目级别（因为块 id 会随分块参数变化而失效）。评测的 K 定死在 8，不跟着线上 `final-top-k` 走——否则我把 topK 从 4 调到 8，Recall 一定涨，但那是口径变松不是链路变好。每次只改一个参数，跑同一份集，两条记录都带完整的参数快照。检索指标是确定性的，同一份数据跑两次结果一模一样，所以 3 个点以上的差异我才认；judge 打的忠实度分不可复现，10 个点以下我当噪声。

**"100 条够吗？"**
做统计显著性检验不够，做方向判断够。它的价值不在样本量，在于**固定**——在线指标每天面对的问题都在变，没法用来归因单个参数。我也清楚它的分辨率上限：100 条、逐条平均，一条用例从全错到全对约等于 1 个百分点，所以我不会拿 +1.5pp 说事。扩集的方式是从在线抽检打低分的真实轮次里挑，不是自己编。

**"评测跑起来会不会影响线上？"**
分三层。检索层和路由层直接调组件，不写任何业务表，随便跑。工具和忠实度那层要真跑 Worker，会执行工具、会写审计表，所以默认关闭，而且两条硬约束：黄金集里禁止出现写操作工具（入库就拦），评测流量用固定的负数 userId，所有在线指标 SQL 都排除它。这两条不做，评测跑几次就会把真实订单改掉，同时把当天的在线指标搞乱。
