### 2.4 搭测试骨架（现在不搭，后面每个阶段的静默错误都只能靠肉眼）

依赖已经齐了，这一步只花十几分钟：`ruoyi-ai/pom.xml` 第 109 行已有 `spring-boot-starter-test`（`scope=test`），根 `pom.xml` 已配好 `maven-surefire-plugin` 3.2.5 和 `jacoco-maven-plugin` 0.8.12（`report` 绑在 `test` 阶段）。**但整个仓库 `src/test` 下一个 Java 文件都没有**——也就是说 `mvn test` 现在能跑、能出覆盖率报告，报告是 0%。

- [ ] 建 `ruoyi-ai/src/test/java/com/ruoyi/ai/`，下面分两个包：
  - [ ] `unit/`——纯逻辑，**不起 Spring 上下文**，毫秒级跑完（路由规则、RRF、累加器、`entryKey`）
  - [ ] `it/`——`@SpringBootTest`，需要真实 MySQL/PG（向量同步、全文检索 SQL）
- [ ] ⚠️ **根 `pom.xml` 里只有 surefire，没有 failsafe**，而 surefire 的默认匹配是 `*Test` / `Test*` / `*Tests` / `*TestCase`——**`*IT` 结尾的类根本不会被执行**。写了一批集成测试却全程绿灯、其实一个都没跑，是这一步最容易踩的坑。两条路选一条：
  - [ ] 给根 `pom.xml` 加 `maven-failsafe-plugin`（推荐）：`*IT` 由它在 `verify` 阶段跑。这样 `mvn test` 只跑秒级单测、`mvn verify` 才跑要连库的那批，正好对上 `unit/` 和 `it/` 的分包
  - [ ] 或者干脆不分插件，集成测试也叫 `XxxTest`，靠标签区分——省一个插件，代价是每次 `mvn test` 都要等数据库
- [ ] `it/` 引 **Testcontainers**（`org.testcontainers:postgresql`，`scope=test`）
  - [ ] **PG 侧用一次性容器**：向量表由 `PgVectorStore.afterPropertiesSet()` 自己建（01 §四），不用准备任何 SQL，接进来几乎零成本，而且测试数据不会脏了 §2.2 那个开发用的库
  - [ ] **MySQL 侧 P0 阶段先连开发库**：Testcontainers 起 MySQL 需要完整的建表脚本，而那套脚本要到 P8 才整理出来（06 §3.3 的 `01-base.sql` + `02-migrations.sql`）。P8 做完之后可以把 MySQL 也切成容器，正好复用那两个文件
  - [ ] `unit/` 保持零依赖、不碰 Docker——这个分界是 `mvn test` 能保持在秒级的前提
- [ ] 加 `.github/workflows/ci.yml`，配置和三个必踩的坑见 §14.4
- [ ] `it/` 里的用例加 `@EnabledIfSystemProperty` 之类的开关，**Docker 没起时跳过而不是整批红掉**（Testcontainers 拿不到 Docker 会直接抛异常）
- [ ] ⚠️ **只要 MySQL 还连着开发库，测试产生的对话数据就会进审计表**，`user_id` 统一用 `-1`，复用 05 §6.3 那套排除机制。否则跑几十次测试之后，Dashboard 上的工具成功率和失败率是被自己的测试污染出来的

> 纪律只有一条：**只给 §十三 那 20 件"会静默出错的事"写测试，不追覆盖率数字。** 那 20 条的共同点是功能看起来能用、数字看起来正常，恰恰是手工验收看不出来的部分；而 Controller 的增删改查手工点一遍就够了，写测试是浪费时间。

## 十二、每个阶段的退路

改造做到一半发现某个决定是错的，这张表决定你要改配置还是回滚代码。

| 能力 | 有配置开关吗 | 怎么退 |

## 十四、验收的三层结构与测试怎么跑

### 14.1 三层各管什么，为什么不能互相替代

每个阶段的验收都是三层叠起来的，**任何一层都盖不住另外两层**：

| 层 | 位置 | 管什么 | 盖不住什么 |
|----|------|--------|-----------|
| 手工冒烟 | 各阶段"验收"里不带"要写的测试"标记的条目 | 跨进程、跨前后端的行为：停掉 PG 还能不能答、重新登录能不能看到菜单、前端有没有先显示"正在处理" | 会静默退化的细节，人不会每次改代码都重新点一遍 |
| 自动化断言 | 各阶段"要写的测试" | 代码对不对：id 规则、metadata 类型、路由优先级、除法顺序、越权校验 | 检索质量好不好——所有断言都通过，Recall 照样可能掉 |
| 黄金集评测 | P6 的 `EvaluationJob` | 检索质量的变化趋势，参数调整有没有真收益 | 原因。它只会告诉你"Recall 降了 4 个点"，不会告诉你是因为 metadata 存了整数导致过滤失效 |

第三层和第二层的关系值得单独说清楚，因为最容易被当成一回事：**黄金集告诉你数字变差了，断言告诉你是哪一行代码变差的。** §十三 那 20 条里，至少有 5 条（#1 #11 #12 #15 #17）的表现形式都是"某个指标不对"——黄金集能看见指标不对，定位到具体原因还是得靠断言。所以调参阶段靠黄金集，改代码阶段靠断言，两者的使用时机也不一样。

### 14.2 命令

多模块项目，`ruoyi-ai` 依赖 `ruoyi-common` 等模块，所以第一次要么带 `-am`，要么先装一遍：

```bash
mvn install -DskipTests            # 首次，或改过 common/framework 之后
mvn -pl ruoyi-ai -am test          # 跑单测（秒级，日常改完代码就跑这个）
mvn -pl ruoyi-ai test -Dtest=IntentRouterTest    # 只跑一个类
mvn -pl ruoyi-ai -am verify        # 跑单测 + 集成测试（要先起 PG 和 MySQL）
```

覆盖率报告在 `ruoyi-ai/target/site/jacoco/index.html`——根 `pom.xml` 已经把 JaCoCo 的 `report` 目标绑在 `test` 阶段，跑完测试自动生成，不用额外命令。

> ⚠️ **现在这份报告是 0%**：工具链齐全（surefire 3.2.5 + JaCoCo 0.8.12 + `spring-boot-starter-test`），但仓库里一个测试文件都没有。配了覆盖率插件却一个用例都没有，比压根没配更显眼——面试官 clone 下来跑一次就看到了。反过来说，**把上面那几十条断言写掉，覆盖率数字自然就有了，而且覆盖的正好是最难讲清楚的那部分逻辑**。被问到"重构这么大，你怎么保证没把原功能弄坏"时，能指着 §十三 那 20 条说"这是我整理的会静默出错的点，其中 5 条我用断言锁住了"，比"我写了单元测试"具体得多。

### 14.3 什么不写测试

写清楚边界，免得把时间花在没收益的地方：

- **不测 Controller 的增删改查。** 知识库页面的 CRUD 手工点一遍就够，接口契约本来就没变（04 §2.1）。
- **不测模型的输出内容。** 模型每次回答都不一样，断言"回复里包含某个词"必然是间歇性失败的测试，比没有测试更糟。要评回答质量，那是黄金集和 judge 的活（05 §五）。
- **不测 Prompt 文本。** 断言"Prompt 里有第 5 条规则"只是把字符串抄了两遍，改 Prompt 时两边一起改，什么也没验证到。
- **不追覆盖率目标。** 不设 80% 之类的门槛。这套测试的目标是守住 §十三 那 20 条，写完就停。

### 14.4 CI（GitHub Actions）

仓库要公开给面试官看，那 CI 就不只是"自动跑测试"，它是**对方点开仓库第一眼能看到的工程素养信号**——一个绿标，和 README 里"我很注重代码质量"这句话的分量完全不同。成本也就一个文件。

`.github/workflows/ci.yml` 的骨架：

```yaml
name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest        # 自带 Docker，Testcontainers 直接可用
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'      # 与 pom 的 java.version 一致
          distribution: 'temurin'
          cache: maven            # 不加这行每次重下全部依赖，四五分钟起
      - run: mvn -B verify        # verify 才会触发 failsafe 跑 it/
```

**三个必踩的坑，全都属于"本地过、CI 挂"那一类：**

1. **CI 里绝对不能配 `DASHSCOPE_API_KEY`。** 一旦配了，集成测试会真的调模型——花钱、慢、而且每次结果不同。但麻烦在于不配也不行：`@SpringBootTest` 起完整上下文时 `AiConfig` 要拿 key 去建 `ChatClient`，缺了直接启动失败，整批 `it/` 红掉。做法是 CI 里给一个假 key（`env: DASHSCOPE_API_KEY: dummy-for-ci`）让上下文能起来，同时**所有 `it/` 用例都不许真的发起模型调用**——需要模型的那些一律 `@MockBean` 掉。这条纪律破了，CI 就会变成一个偷偷烧 token 的定时任务。

2. **字符编码。** 本地是 Windows、CI 是 Linux，而 **JDK 17 的默认字符集取自平台**（JDK 18 才改成一律 UTF-8）。`pom.xml` 里的 `project.build.sourceEncoding=UTF-8` 只管编译，不管测试运行时的 `file.encoding`。所以断言中文文案的用例（路由关键词、错误提示语）完全可能本地绿、CI 红，或者反过来。给 surefire 和 failsafe 都显式设 `<argLine>-Dfile.encoding=UTF-8</argLine>`。这和 §十三 #18 是同一个根因的两个现场。

3. **MySQL 也得有。** `it/AiMetricsIT` 要查审计表，只起 PG 不够。P8 之前 CI 里用 `services:` 起一个 MySQL 8 并手动导表；P8 之后改成 Testcontainers 挂载 `docker/mysql-init/` 里那两个脚本（06 §3.3），本地和 CI 就是同一份代码说了算。

> 如果 CI 一时跑不通，先让它只跑 `mvn -B test`（纯单测，不碰任何数据库）。**一个只跑单测的绿标，远好过一个长期挂红的完整流水线**——后者给面试官的印象是负的。
