# 06 · 部署设计（本地开发 → Docker）

> 按已确认的顺序：**先本地开发跑通，最后 Docker 化。**
> 本文所有片段都对着仓库实际情况写，不是模板抄的：后端 `ruoyi-admin` 的 `packaging` 是 **jar**、`finalName=ruoyi-admin`，产物为 `ruoyi-admin/target/ruoyi-admin.jar`，端口 **8080**、`context-path=/`；前端是 **Vite** 工程，构建产物在 `ruoyi-ui/dist`，生产环境请求前缀是 **`/prod-api`**（`ruoyi-ui/.env.production` 的 `VITE_APP_BASE_API`）；上传文件由后端以 **`/profile/**`** 暴露（`Constants.RESOURCE_PREFIX`，`ResourcesConfig` 映射到 `ruoyi.profile` 目录）。

---

## 一、本地开发运行清单

| 组件 | 需求 | 说明 |
|------|------|------|
| JDK | 17 | 当前项目 |
| MySQL | 8.x | 业务库（RuoYi 既有）。p95 指标用了窗口函数，**必须 8.x** |
| **PostgreSQL(带 pgvector)** | PG 16 + pgvector | 向量库（新增，见 01） |
| Redis | 6/7 | 缓存 + 一次性 ticket + 评测互斥锁 |
| 前端 | Node + npm | `ruoyi-ui`（Vite） |
| 模型 API | DashScope(Qwen) | `DASHSCOPE_API_KEY` |

> **已确认的部署决策**：文档/图片走**本地上传目录 + 卷挂载**（路径全部环境变量化，不留硬编码盘符）；向量库用官方镜像 `pgvector/pgvector:pg16`；MySQL 只管业务与评测数据，PG 只管向量。

### 1.1 本地起 PG + pgvector

```bash
docker run -d --name ai-vector \
  -e POSTGRES_DB=ai_vector \
  -e POSTGRES_USER=vector \
  -e POSTGRES_PASSWORD=<你的密码> \
  -p 5432:5432 \
  pgvector/pgvector:pg16
```
镜像自带 `vector` 扩展，不用手动 `CREATE EXTENSION`。若本机不能用 Docker，再走原生安装：装 PG 16 → `CREATE DATABASE ai_vector;` → 在该库里 `CREATE EXTENSION IF NOT EXISTS vector;`。

**建库之后**：向量表由 `PgVectorConfig` 里手写的 Bean 创建（01 §四），配置键是 **`smart-cs.vector-store.pg.*`**；其中 `initialize-schema: true` 让 `PgVectorStore.afterPropertiesSet()` 自动建表 + 建 HNSW 索引。

> ⚠️ **别写 `spring.ai.vectorstore.pgvector.*`**。那套键只有 pgvector **starter** 的自动配置会读，而本项目刻意不用 starter（01 §二：starter 会拿 `@Primary` 的 MySQL `JdbcTemplate` 去建向量表）。写了既不报错也不生效，是最难查的一类配置错误。

### 1.2 后端启动

1. `application.yml` 按 01 §三 / 02 §三 / 03 §八 / 05 §6.2 补齐配置块；
2. 环境变量至少给 `DASHSCOPE_API_KEY`、`PG_PWD`、`PROFILE_DIR`、`UPLOAD_DIR`（见 §二）；
3. `mvn clean package -DskipTests` 或 IDE 直接启动 `ruoyi-admin`。

### 1.3 前端

`cd ruoyi-ui && npm install && npm run dev`（开发态走 `/dev-api` 代理，见 `vite.config.js`）。

### 1.4 验收

能登录、能对话、能查商品/订单、能上传文档并问出其中内容、Dashboard 指标可见、能跑一次离线评测。

## 二、配置外置与环境变量

### 2.1 P0 必须改掉的三处硬编码

全仓 grep 确认过：写死的 Windows 盘符只存在于 `application.yml` **一个文件**，Java 代码里一处都没有。所以 P0 是纯配置改动，零代码风险。

| 配置项 | 现状 | 改成 |
|--------|------|------|
| `ruoyi.profile` | `D:/ruoyi/uploadPath` | `${PROFILE_DIR:D:/ruoyi/uploadPath}` |
| `smart-cs.upload.path` | `D:/ruoyi/uploadPath/ai-knowledge/` | `${UPLOAD_DIR:${PROFILE_DIR:D:/ruoyi/uploadPath}}/ai-knowledge/` |
| `smart-cs.vector-store.path` | `D:/ruoyi/uploadPath/vectorstore.json` | P1 随 `SimpleVectorStore` 一起删除；P0 先跟着改成 `${PROFILE_DIR:D:/ruoyi/uploadPath}/vectorstore.json` |

两个细节值得说明：

1. **默认值保留原来的 `D:/ruoyi/uploadPath`**，不换成 `./data/upload` 这类相对路径。不给环境变量时行为与今天完全一致，已经上传的图片和知识文档不会突然 404。
2. `UPLOAD_DIR` 的默认值**嵌套引用** `PROFILE_DIR`（Spring 支持 `${A:${B:兜底}}`），于是 Docker 里只挂一个卷、只给一个变量，知识库文档自动落在同一个卷下。

> `ruoyi.profile` 被 `ResourcesConfig.addResourceHandlers()` 拿去把磁盘目录映射成 `/profile/**`（`Constants.RESOURCE_PREFIX = "/profile"`）。改它等于改静态资源根目录，**改完必须回归"上传图片 → 页面能显示"**这条链路，它最容易漏测。

### 2.2 环境变量总表

`✔` = 不给就跑不起来、或者行为不对。

| 变量 | 落到哪个配置 | 默认值 | 本地 | Docker |
|------|------------|--------|------|--------|
| `DASHSCOPE_API_KEY` | `spring.ai.openai.api-key` | `sk-placeholder` | ✔ | ✔ |
| `PROFILE_DIR` | `ruoyi.profile` | `D:/ruoyi/uploadPath` | — | ✔ |
| `UPLOAD_DIR` | `smart-cs.upload.path` 前缀 | 同 `PROFILE_DIR` | — | — |
| `PG_HOST` / `PG_PORT` / `PG_DB` / `PG_USER` | `smart-cs.vector-store.pg.*`（01 §三） | `localhost` / `5432` / `ai_vector` / `vector` | — | ✔ |
| `PG_PWD` | 同上 | **无默认，缺了直接启动失败** | ✔ | ✔ |
| `MYSQL_URL` / `MYSQL_USER` / `MYSQL_PWD` | `spring.datasource.druid.master.*` | 现仓库里的 `localhost:3306/sqz-smart-ai` + `root/123456` | — | ✔ |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PWD` | `spring.data.redis.*` | `localhost` / `6379` / 空 | — | ✔ |
| `AI_WORKER_MODEL` / `AI_ROUTER_MODEL` / `AI_JUDGE_MODEL` | `smart-cs.model.*`（02 §三） | 均为 `qwen3.5-plus-2026-02-15` | — | — |
| `TOKEN_SECRET` | `token.secret` | 仓库里那串 `abcdefghijklmnopqrstuvwxyz` | — | ✔ |
| `SPRING_PROFILES_ACTIVE` | — | `druid,dev` | — | `druid,prod` |

`application-druid.yml` 里的三项要顺手改成占位符，否则 Docker 里只能靠 `SPRING_DATASOURCE_DRUID_MASTER_URL` 这种长环境变量名去覆盖（`DruidConfig.masterDataSource()` 上挂着 `@ConfigurationProperties("spring.datasource.druid.master")`，宽松绑定确实认这个名字，但可读性差太多）：

```yaml
master:
    url: ${MYSQL_URL:jdbc:mysql://localhost:3306/sqz-smart-ai?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=true&serverTimezone=GMT%2B8}
    username: ${MYSQL_USER:root}
    password: ${MYSQL_PWD:123456}
```

### 2.3 本地怎么给这些变量

IDEA：`Run/Debug Configurations → Environment variables`，一行填完：

```
DASHSCOPE_API_KEY=sk-xxx;PG_PWD=xxx
```

命令行（PowerShell，只在当前会话生效）：

```powershell
$env:DASHSCOPE_API_KEY="sk-xxx"; $env:PG_PWD="xxx"
mvn -pl ruoyi-admin -am spring-boot:run
```

### 2.4 这几样东西不许进仓库

`DASHSCOPE_API_KEY`、`PG_PWD`、`MYSQL_PWD`、`TOKEN_SECRET`。P-1 建 git 仓库时（07 §1.1）先确认 `.gitignore` 覆盖了本地环境变量文件，再提交第一个 commit。

> 顺带一句实话：**当前仓库里 `application-druid.yml` 的 `root/123456`、`token.secret`、Druid 监控台的 `ruoyi/123456` 都是明文**。作品项目里这不致命，但既然要给面试官看代码，把它们换成占位符 + 环境变量是个很便宜的加分项——被问到"配置和密钥怎么管的"时有话可说。

## 三、Docker 化（P8）

前置条件：P0~P7 全部做完且本地能跑通。**Docker 只解决"换台机器也能起来"，不解决任何功能问题**——本地跑不通的东西装进容器只会更难查。

目录结构（新增文件，都放仓库根目录）：

```
Dockerfile                 # 后端
ruoyi-ui/Dockerfile        # 前端（多阶段：node 构建 → nginx 托管）
docker/nginx.conf
docker/mysql-init/01-base.sql        # sql/sqz-smart-ai0314.sql 的副本（最新全量导出）
docker/mysql-init/02-migrations.sql  # 本轮两个迁移脚本合并（05 §三）
docker-compose.yml
.env                       # 只放在本机，不进仓库
```

### 3.1 两个 Dockerfile

**后端**：

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY ruoyi-admin/target/ruoyi-admin.jar app.jar
ENV TZ=Asia/Shanghai \
    LANG=C.UTF-8 \
    JAVA_OPTS="-Xms512m -Xmx1024m -Dfile.encoding=UTF-8 -Duser.timezone=Asia/Shanghai"
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]
```

三个参数不是抄模板抄来的：

- **`-Dfile.encoding=UTF-8` 必须显式给**。JDK 17 的默认字符集仍取自平台，容器里通常是 POSIX/ASCII，中文日志、中文文件名、甚至中文响应体都会乱码。JDK 18 才把默认值改成 UTF-8，本项目是 17，**这一条不加就会踩**。
- **`TZ` + `-Duser.timezone` 都给**。JDBC URL 里写着 `serverTimezone=GMT+8`，容器默认 UTC，不对齐的话审计表和指标的时间会整体偏 8 小时，而所有"最近 7 天"的指标 SQL 都按时间过滤。
- 产物路径写死 `ruoyi-admin/target/ruoyi-admin.jar` 是有依据的：`ruoyi-admin/pom.xml` 的 `packaging` 是 `jar`，`finalName` 取 `${project.artifactId}`。

> `spring-boot-devtools` 在 `ruoyi-admin/pom.xml` 里是 `optional`，而 `spring-boot-maven-plugin` 的 `repackage` 默认排除 devtools，所以它不会被打进 jar，`spring.devtools.restart.enabled: true` 在容器里是死配置，不用管。

构建顺序（Dockerfile 里不编译，避免每次构建都重下 Maven 依赖）：

```powershell
mvn clean package -DskipTests   # 产出 ruoyi-admin/target/ruoyi-admin.jar
docker compose build
```

**前端**（多阶段：node 构建 → nginx 托管，`ruoyi-ui/Dockerfile`）：

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build:prod

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
```

> ⚠️ 构建命令是 **`npm run build:prod`**，不是 `npm run build`——`ruoyi-ui/package.json` 里只有 `dev` / `build:prod` / `build:stage` / `preview`，写错直接构建失败。
> `nginx.conf` 故意不 `COPY` 进镜像，而是用 compose 的 `volumes` 挂进去（下面 §3.2）。改一行反代配置不用重新构建镜像，`docker compose restart nginx` 就生效。
> `.env.production` 里 `VITE_BUILD_COMPRESS = gzip`，构建会额外产出 `.gz` 文件，所以 nginx 里要开 `gzip_static on` 才吃得到——不开就是白压。

### 3.2 `docker-compose.yml` 与 `nginx.conf`

**compose** —— 五个服务：`mysql` / `redis` / `postgres` / `backend` / `nginx`。

```yaml
services:
  mysql:
    image: mysql:8.0
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_general_ci
             --default-time-zone=+08:00
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_PWD}
      MYSQL_DATABASE: sqz-smart-ai
      TZ: Asia/Shanghai
    volumes:
      - mysqldata:/var/lib/mysql
      - ./docker/mysql-init:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-p${MYSQL_PWD}"]
      interval: 10s
      retries: 20

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      retries: 10

  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: ai_vector
      POSTGRES_USER: vector
      POSTGRES_PASSWORD: ${PG_PWD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U vector -d ai_vector"]
      interval: 10s
      retries: 10

  backend:
    build: .
    environment:
      SPRING_PROFILES_ACTIVE: druid,prod
      MYSQL_URL: jdbc:mysql://mysql:3306/sqz-smart-ai?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=false&serverTimezone=GMT%2B8
      MYSQL_USER: root
      MYSQL_PWD: ${MYSQL_PWD}
      REDIS_HOST: redis
      PG_HOST: postgres
      PG_PWD: ${PG_PWD}
      DASHSCOPE_API_KEY: ${DASHSCOPE_API_KEY}
      TOKEN_SECRET: ${TOKEN_SECRET}
      PROFILE_DIR: /data/upload
    volumes:
      - upload:/data/upload
      - logs:/home/ruoyi/logs
    depends_on:
      mysql: { condition: service_healthy }
      redis: { condition: service_healthy }
      postgres: { condition: service_healthy }

  nginx:
    build:
      context: ./ruoyi-ui
    ports:
      - "80:80"
    volumes:
      - ./docker/nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - backend

volumes:
  mysqldata:
  pgdata:
  upload:
  logs:
```

四处值得解释：

- **`depends_on` 必须用 `condition: service_healthy`**，光写服务名只保证"容器启动了"，不保证数据库能连。后端启动时要连 MySQL、Redis、PG 三家，任何一家没就绪就是启动失败。
- **MySQL 连接串把 `useSSL` 改成 `false`**。容器内网通信，开 TLS 只是白付握手开销；仓库里现在写的是 `useSSL=true`，本地连本机也无所谓，进 compose 后建议关掉。
- **`PROFILE_DIR: /data/upload` 配合 `upload` 卷**。上传的图片和知识文档都落在这个卷里，`docker compose down` 不会丢；只有 `down -v` 才会删。
- **`logs` 卷挂到 `/home/ruoyi/logs`**：`logback-spring.xml` 里 `log.path` 写死的就是这个路径，不挂卷日志会随容器一起消失。
- 三个数据库**都不映射宿主端口**。要连进去查数据用 `docker compose exec mysql mysql -uroot -p`，别为了图方便把 3306/5432 暴露到宿主机。

**nginx** —— `docker/nginx.conf`：

```nginx
server {
    listen 80;
    server_name  _;
    client_max_body_size 20m;          # 必须 ≥ max-request-size(20MB)，否则大文件上传 413
    gzip_static on;                     # 吃 vite 构建产出的 .gz

    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;   # history 路由刷新不 404
    }

    # 前端生产环境请求前缀是 /prod-api（ruoyi-ui/.env.production）
    location /prod-api/ {
        proxy_pass http://backend:8080/;   # 末尾斜杠负责剥掉 /prod-api 前缀
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;

        # ↓ SSE 与长耗时评测接口的关键四行
        proxy_set_header Connection        '';
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
    }
}
```

这份配置里每一行都对着本项目的一个具体事实：

| 配置 | 为什么 |
|------|--------|
| `location /prod-api/` + `proxy_pass` 带末尾斜杠 | `ruoyi-ui/.env.production` 的 `VITE_APP_BASE_API = '/prod-api'`，而后端 `context-path: /`。斜杠不写 = 后端收到 `/prod-api/ai/chat/stream` → 全站 404 |
| `client_max_body_size 20m` | `spring.servlet.multipart.max-request-size: 20MB`。nginx 默认只有 1m，知识库上传大文档会在 nginx 层就被 413 拦掉，后端日志里干干净净什么都看不到 |
| `proxy_buffering off` + `Connection ''` + `proxy_http_version 1.1` | SSE 必需。nginx 默认会缓冲上游响应，`intent`、`tool_call`、`card_data` 这些事件会被攒住一起吐，"实时感"直接消失——而这正是 00 §二"延迟优先"里最便宜的那一招 |
| `proxy_read_timeout 600s` | 两个地方要它：SSE 连接本身（后端 `SseEmitter` 是 300 秒），以及 `POST /ai/eval/run` 这个长耗时同步接口（05 §6.7，开了 `run-agent` 会跑到几分钟）。nginx 默认 60s，超了前端拿 504、后端还在跑、Redis 锁还占着，界面上看起来就是"评测坏了" |
| 不需要单独的 `/profile` location | 前端所有图片地址都是 `import.meta.env.VITE_APP_BASE_API + '/profile/xxx'`（见 `ImagePreview`、`ImageUpload`、`user.js`），走的还是 `/prod-api/`，由后端的 `ResourcesConfig` 映射到磁盘。**开发态 `vite.config.js` 里那条 `/profile` 代理是给 dev server 用的，别照搬进 nginx** |

> 保险起见，后端在 SSE 响应上再加一个 `X-Accel-Buffering: no` 响应头。这样即使换了台机器、nginx 配置漏了 `proxy_buffering off`，SSE 也不会被缓冲。一行代码换掉一类难查的环境问题，很划算。

### 3.3 MySQL 初始化脚本

`docker-entrypoint-initdb.d` 的两条规则决定了脚本必须怎么命名：

1. **只在数据卷为空时执行一次**。改了脚本想重新初始化，必须 `docker compose down -v`（**会删库，问清楚再敲**）。
2. **按文件名字典序执行**。

第 2 条是个真实的坑：仓库里最新的全量导出叫 `sqz-smart-ai0314.sql`，本轮迁移脚本叫 `2026-09-03_*.sql`。数字排在字母前面，直接挂进去的话**迁移脚本会先跑**，而那时候 `ai_chat_turn_audit` 还不存在 → `ALTER TABLE` 报表不存在。所以复制进 `docker/mysql-init/` 时统一改名加序号：

| 文件 | 来源 |
|------|------|
| `01-base.sql` | `sql/sqz-smart-ai0314.sql`（最新全量导出，含表结构 + 演示数据） |
| `02-migrations.sql` | `sql/2026-09-03_多智能体改造_审计扩展与评测表.sql`（05 §三）+ 评测菜单权限（05 §3.5） |

全量导出是 Navicat 生成的，开头只有 `SET NAMES utf8mb4;` 和 `SET FOREIGN_KEY_CHECKS = 0;`，**没有 `CREATE DATABASE` / `USE`**，所以库名完全由 compose 里的 `MYSQL_DATABASE: sqz-smart-ai` 决定，两边必须一致。

PG 侧不需要初始化脚本：`pgvector/pgvector:pg16` 自带 `vector` 扩展，向量表和 HNSW 索引由 `PgVectorConfig` 在启动时建（01 §四，`initialize-schema: true`）。只有 01 §5.1 那个全文检索索引脚本要在**第一次启动之后**手动跑一次——它依赖 `vector_store` 表已经存在。

### 3.4 数据卷与备份

| 卷 | 装什么 | 丢了会怎样 |
|----|--------|-----------|
| `mysqldata` | 业务库 + 审计 + 黄金集 + 评测结果 | 演示数据、真实提问、所有历史指标全没 —— **最要紧的一个** |
| `pgdata` | 向量库 | 可以靠 `POST /ai/knowledge/rebuild-vector?truncate=true` 从 MySQL 重建，代价是一次全量 embedding |
| `upload` | 上传的图片与知识文档 | 商品图 404；知识条目还在但原始文档没了 |
| `logs` | 后端日志 | 只影响排查 |

演示前备份就两条命令：

```powershell
docker compose exec -T mysql mysqldump -uroot -p"$env:MYSQL_PWD" --default-character-set=utf8mb4 sqz-smart-ai > backup-mysql.sql
docker compose exec -T postgres pg_dump -U vector ai_vector > backup-pg.sql
```

> `pgdata` 可重建、`mysqldata` 不可重建，这个不对称决定了备份优先级。演示前一天只来得及备一个的话，备 MySQL。

## 四、上线前要改掉的几个默认值

这几项在本地开发无所谓，但只要机器能被别人访问就都是问题。改动量都是一行。

| 项 | 现状 | 建议 |
|----|------|------|
| `springdoc.swagger-ui.enabled` | `true` | 生产 `false`。开着等于把全部接口清单和参数结构公开 |
| Druid 监控台 `/druid/*` | 开启，账号 `ruoyi/123456` | 关掉 `statViewServlet.enabled`，或换强密码 + nginx 上禁掉这个路径。它能看到全部 SQL 和数据源配置 |
| `token.secret` | 明文 `abcdefghijklmnopqrstuvwxyz` | 换 `${TOKEN_SECRET:...}`。JWT 密钥公开等于任何人都能签发有效 token |
| `logging.level.com.ruoyi` / `org.springframework.ai` | `debug` | 生产降 `info`。`spring.ai` 的 debug 会把每轮完整 prompt 打进日志，既是磁盘噪音也是信息泄露面（02 §9.1 也提到要清掉 `AiRequestLoggingInterceptor` 里打全量请求体那段） |
| `CorsFilter` 允许 `*` | 允许全部来源 | 前后端同源反代之后本就不需要跨域，可收窄成具体域名 |

> 这不是"要不要做安全加固"的问题。面试时被问"你这个东西直接放公网会怎样"，能一条条说出上面这些点并说明改法，比嘴上说"我很注重安全"有用得多。

## 五、部署后验收

按顺序走一遍，任何一步不过就不用往下走了。

| # | 动作 | 通过标准 |
|---|------|---------|
| 1 | `docker compose up -d` | 五个容器都是 `healthy` / `running`，`docker compose logs backend` 无异常堆栈 |
| 2 | 打开 `http://<host>/` 登录 | 首页正常，无 404、无跨域报错 |
| 3 | 问一句"你好" | 有回复；**日志里没有任何模型调用**（规则路由生效的最直观证据，00 §五 P4） |
| 4 | 问"推荐个手机" | 命中 `sales-advisor`，出商品卡片；审计表 `agent_id` / `intent` / `route_source` 有值 |
| 5 | 观察 SSE | `intent` 事件先到、正文后到（缓冲没被开启的证据）；整段回复不是一次性突然出现 |
| 6 | 上传一个文档并提问 | 能问出文档里的内容；`GET /ai/knowledge/vector-store-status` 的 `vectorCount` 增加 |
| 7 | 上传一张商品图 | 页面能显示（`PROFILE_DIR` + 卷挂载 + `/profile` 映射三者都对） |
| 8 | 说"取消我的订单 ORDxxx" | 出确认卡片，`ai_pending_action` 落一行 `PENDING`，**订单状态未变**；点确认后才真的取消 |
| 9 | 连续对话 20 轮 | 无"系统暂时繁忙"；Dashboard 的失败率 / 重试率 / 超时率 / p95 都有数 |
| 10 | 跑一次 `POST /ai/eval/run` | 不超时（`proxy_read_timeout` 生效），结果落 `ai_eval_result`，能打出同集对比表（05 §7.2） |
| 11 | `docker compose restart backend` | 起来后检索仍正常（向量在 PG 里，不再依赖 `vectorstore.json`）、上传的文件还在 |

第 11 步是整个改造最实在的一条验收：**重启后检索还在**。改造前它依赖一个本地 json 文件，换台机器就得重建。

## 六、风险与规避

| 风险 | 触发条件 | 规避 |
|------|----------|------|
| PG 数据源抢走 `@Primary` | 手写 PG `DataSource` 时加了 `@Primary`，或误引 pgvector starter | PG 的 `DataSource` / `JdbcTemplate` 一律只用 `@Bean("pgVector...")` 具名注入，**主数据源必须仍是 MySQL 的 `dynamicDataSource`**（01 §二、§四） |
| 容器里中文乱码 | 漏了 `-Dfile.encoding=UTF-8` | §3.1 已固定；验收第 6 步（上传中文文档）能立刻暴露 |
| 时间差 8 小时 | 容器 UTC vs JDBC `serverTimezone=GMT+8` | 后端 `TZ` + MySQL `--default-time-zone=+08:00` 两边都设 |
| SSE 被缓冲 | nginx 少了 `proxy_buffering off` | §3.2 配置 + 后端补 `X-Accel-Buffering: no` 双保险 |
| 大文件上传 413 | nginx 默认 `client_max_body_size 1m` | 设 20m，与 `max-request-size` 对齐 |
| 评测接口 504 | `proxy_read_timeout` 默认 60s | 设 600s；同时前端按钮点击后置灰（04 §3.2） |
| 迁移脚本先于建表执行 | 直接把 `2026-09-03_*.sql` 丢进 `mysql-init` | 改名 `01-base.sql` / `02-migrations.sql`（§3.3） |
| 改了 init 脚本却不生效 | 数据卷已有数据，初始化只跑一次 | 明确知道要删库时才 `down -v`；否则手动 `exec` 进容器执行 |
| 换台机器 `PG_PWD` 没给 | 该项无默认值 | 启动直接失败（这是 01 §三 故意的设计），照 §2.2 补齐 |
| 卷被误删 | `docker compose down -v` | `-v` 只在明确要重置时用；给人演示前先按 §3.4 备份 MySQL |
