# 01 · 向量库与数据库设计（pgvector 落地）

> 本文解决一件事：**把向量存储从内存 JSON 的 `SimpleVectorStore` 换成 PostgreSQL + pgvector，并且不把 RuoYi 现有的 MySQL 数据源搞坏。**
> 文中所有 API 与 SQL 都对照 Spring AI 1.0.0 的 `PgVectorStore` 源码核实过，可直接照抄。

---

## 一、为什么换（一句话版）

| 维度 | 现状 `SimpleVectorStore` | 换成 pgvector |
|------|-------------------------|--------------|
| 索引 | 无 ANN，全量线性比对 | HNSW 近似最近邻索引 |
| 持久化 | 单个 `vectorstore.json`，每次写都 `save(File)` 全量落盘 | 表 + 事务，单条 upsert |
| 崩溃恢复 | 文件损坏就得全量重建 | PG 自身保障 |
| 元数据过滤 | 支持有限 | `metadata::jsonb @@ jsonpath`，可与向量条件同查 |
| 混合检索 | 只有向量 | 同库内再加一路 `tsvector` 全文，一次往返 |
| 并发写 | 靠 `ReentrantReadWriteLock` 自己扛 | 交给数据库 |

现状代码里最刺眼的一点：`KnowledgeService.addToVectorStore()` 每加一条知识就调一次 `vectorStore.save(new File(path))`，**全量重写整个 json 文件**。知识条目一多，写入耗时随总量线性增长。

> 面试话术："我把向量存储从内存 JSON 换到 pgvector。真正的动机不是'用个更高级的库'，是原实现每写一条知识就全量重写一次 json 文件、且重启依赖文件完好。换到 PG 之后写入是单条 upsert、检索走 HNSW 索引、元数据过滤能下推到 SQL，顺带还能在同一张表上加一路全文检索做混合召回。"

## 二、依赖：**不要用 starter**

```xml
<!-- ruoyi-ai/pom.xml -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-pgvector-store</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

版本由根 `pom.xml` 里已有的 `spring-ai-bom`（1.0.0）统一管理，不要自己写 `<version>`。

**为什么不是 `spring-ai-starter-vector-store-pgvector`：**
starter 会引入 `spring-ai-autoconfigure-vector-store-pgvector`，它按"容器里唯一的 `JdbcTemplate`"来建 `PgVectorStore`。而本项目里 `DruidConfig.dataSource()` 声明的 `dynamicDataSource` 带 `@Primary`（指向 **MySQL**），自动配置拿到的就是 MySQL 的 `JdbcTemplate` —— 于是它会试图在 MySQL 上执行 `CREATE EXTENSION vector`，必然失败。
用非 starter 模块 + 手写 Bean，PG 连接完全由我们控制，也不影响 `DashboardController` 注入的那个（MySQL）`JdbcTemplate`。

## 三、配置项（`application.yml` 追加）

```yaml
smart-cs:
  # 原 vector-store.path（D:/ruoyi/uploadPath/vectorstore.json）随 SimpleVectorStore 一起删除
  upload:
    path: ${UPLOAD_DIR:${PROFILE_DIR:D:/ruoyi/uploadPath}}/ai-knowledge/
  vector-store:
    pg:
      url: jdbc:postgresql://${PG_HOST:localhost}:${PG_PORT:5432}/${PG_DB:ai_vector}
      username: ${PG_USER:vector}
      password: ${PG_PWD}            # 必须由环境变量提供，不写进仓库
      schema-name: public
      table-name: vector_store
      dimensions: 1024               # 必须等于 text-embedding-v3 的输出维度
      initialize-schema: true        # 首次启动自动建表 + 建 HNSW 索引
      max-document-batch-size: 200
      pool-size: 5                   # 向量库并发很低，5 足够
```

> ⚠️ `dimensions` 与 embedding 模型必须一致。当前 `spring.ai.openai.embedding.options.model=text-embedding-v3`，按 1024 维配置。**换模型或换维度必须重建表和索引**，否则写入直接报维度不匹配。
> ⚠️ `password` 不给默认值，启动时缺 `PG_PWD` 就直接失败——这是故意的，避免"本地能跑、换机器连不上却不报错"。
> `upload.path` 的默认值嵌套引用 `PROFILE_DIR`，兜底仍是现在的 `D:/ruoyi/uploadPath`：不给任何环境变量时行为与今天一致，Docker 里只挂一个卷就够（06 §2.1）。

## 四、核心配置代码：`PgVectorConfig`

新增 `ruoyi-ai/src/main/java/com/ruoyi/ai/config/PgVectorConfig.java`，**替换掉现有的 `VectorStoreConfig`**（后者的 `SimpleVectorStore` Bean 删除）。

```java
package com.ruoyi.ai.config;

import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.embedding.EmbeddingModel;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.pgvector.PgVectorStore;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.core.JdbcTemplate;

import javax.sql.DataSource;

/**
 * PG 向量库配置。
 *
 * 关键约束：
 * 1) RuoYi 的 dynamicDataSource 带 @Primary 且指向 MySQL，这里的数据源必须是「非 Primary」，
 *    否则 MyBatis / DashboardController 注入的 JdbcTemplate 会被换成 PG，业务查询全挂。
 * 2) 因此也不能用 pgvector 的 starter（它按唯一 JdbcTemplate 装配），只能手写 Bean。
 * 3) PgVectorStore 实现了 InitializingBean，声明成 Bean 后会自动执行建表/建索引。
 */
@Configuration
public class PgVectorConfig {

    private static final Logger log = LoggerFactory.getLogger(PgVectorConfig.class);

    @Value("${smart-cs.vector-store.pg.url}")
    private String url;
    @Value("${smart-cs.vector-store.pg.username}")
    private String username;
    @Value("${smart-cs.vector-store.pg.password}")
    private String password;
    @Value("${smart-cs.vector-store.pg.pool-size:5}")
    private int poolSize;
    @Value("${smart-cs.vector-store.pg.schema-name:public}")
    private String schemaName;
    @Value("${smart-cs.vector-store.pg.table-name:vector_store}")
    private String tableName;
    @Value("${smart-cs.vector-store.pg.dimensions:1024}")
    private int dimensions;
    @Value("${smart-cs.vector-store.pg.initialize-schema:true}")
    private boolean initializeSchema;
    @Value("${smart-cs.vector-store.pg.max-document-batch-size:200}")
    private int maxDocumentBatchSize;

    /** 向量库专用连接池（HikariCP 由 spring-boot-starter-jdbc 带入，无需额外依赖） */
    @Bean("pgVectorDataSource")
    public DataSource pgVectorDataSource() {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl(url);
        cfg.setUsername(username);
        cfg.setPassword(password);
        cfg.setMaximumPoolSize(poolSize);
        cfg.setMinimumIdle(1);
        cfg.setConnectionTimeout(10_000);
        cfg.setPoolName("pgVectorPool");
        log.info("向量库数据源初始化 - url: {}, poolSize: {}", url, poolSize);
        return new HikariDataSource(cfg);
    }

    @Bean("pgVectorJdbcTemplate")
    public JdbcTemplate pgVectorJdbcTemplate(@Qualifier("pgVectorDataSource") DataSource ds) {
        return new JdbcTemplate(ds);
    }

    @Bean
    public VectorStore vectorStore(@Qualifier("pgVectorJdbcTemplate") JdbcTemplate pgJdbc,
                                   EmbeddingModel embeddingModel) {
        log.info("初始化 PgVectorStore - table: {}.{}, dimensions: {}, index: HNSW/COSINE",
                schemaName, tableName, dimensions);
        return PgVectorStore.builder(pgJdbc, embeddingModel)
                .schemaName(schemaName)
                .vectorTableName(tableName)
                // 关键：默认是 UUID，会对文档 id 执行 UUID.fromString()；
                // 我们用业务键 knowledge_{id}_c{n}，必须显式改成 TEXT
                .idType(PgVectorStore.PgIdType.TEXT)
                // 显式给维度，避免启动时为探测维度多打一次 embedding 接口
                .dimensions(dimensions)
                .distanceType(PgVectorStore.PgDistanceType.COSINE_DISTANCE)
                .indexType(PgVectorStore.PgIndexType.HNSW)
                .initializeSchema(initializeSchema)
                .maxDocumentBatchSize(maxDocumentBatchSize)
                .build();
    }
}
```

## 五、表结构（由 `PgVectorStore` 自动创建，等价 DDL）

`initialize-schema: true` 时，`PgVectorStore.afterPropertiesSet()` 实际执行的就是下面这些（照源码抄的，写在文档里方便对账和手工建库）：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS hstore;
CREATE SCHEMA IF NOT EXISTS public;

CREATE TABLE IF NOT EXISTS public.vector_store (
    id        text PRIMARY KEY,      -- idType=TEXT 的结果；默认 UUID 模式是 uuid DEFAULT uuid_generate_v4()
    content   text,
    metadata  json,                  -- 注意是 json 而非 jsonb，过滤时框架自己 ::jsonb
    embedding vector(1024)
);

CREATE INDEX IF NOT EXISTS spring_ai_vector_index
    ON public.vector_store USING HNSW (embedding vector_cosine_ops);
```

框架实际跑的读写 SQL（了解它才能看懂性能与语义）：

| 操作 | SQL 形态 |
|------|---------|
| 写入 | `INSERT INTO vector_store (id, content, metadata, embedding) VALUES (?,?,?::jsonb,?) ON CONFLICT (id) DO UPDATE SET ...` → **同 id 覆盖，天然幂等** |
| 检索 | `SELECT *, embedding <=> ? AS distance FROM vector_store WHERE embedding <=> ? < ? [AND metadata::jsonb @@ '...'::jsonpath] ORDER BY distance LIMIT ?` |
| 阈值语义 | 传入的 `similarityThreshold` 被换算成 `distance < 1 - threshold`；返回的 `score = 1 - distance` |
| 按条件删 | `DELETE FROM vector_store WHERE metadata::jsonb @@ '...'::jsonpath` |

### 5.1 需要我们自己加的两个索引（PG 侧迁移脚本）

新增 `sql/2026-09-02_向量库全文检索与元数据索引.sql`（**在 PG 库执行，不是 MySQL**）：

```sql
-- 全文检索路（混合检索用，见 03）。simple 配置不做中文分词，
-- 只负责型号/SKU/英文词这类精确命中，中文语义由向量路负责。
CREATE INDEX IF NOT EXISTS idx_vector_store_content_fts
    ON public.vector_store USING GIN (to_tsvector('simple', content));

-- 元数据过滤路：PgVectorStore 用 metadata::jsonb @@ jsonpath，
-- 对应的表达式索引必须写成 (metadata::jsonb) 才能命中。
CREATE INDEX IF NOT EXISTS idx_vector_store_metadata_path
    ON public.vector_store USING GIN ((metadata::jsonb) jsonb_path_ops);
```

> 这两个索引必须在**向量表已存在之后**执行，即先启动一次应用让框架建表，再跑脚本。

## 六、文档 id 与 metadata 约定（**全项目统一，改这里等于改契约**）

### 6.1 id 规则

| 来源 | id 格式 | 例子 |
|------|---------|------|
| 知识条目分块 | `knowledge_{knowledgeId}_c{chunkIndex}` | `knowledge_33_c0` |
| 上传文档分块 | `doc_{docId}_c{chunkIndex}` | `doc_7_c12` |

用业务键而不是随机 UUID，换来两件事：**重复入库自动覆盖**（`ON CONFLICT`）、**排查时一眼知道这块来自哪条知识**。

### 6.2 metadata 规则：**所有值一律存字符串**

| 键 | 说明 |
|----|------|
| `knowledgeId` | 关联 `ai_knowledge.knowledge_id`，删除/溯源用 |
| `category` | `FAQ` / `POLICY` / `PRODUCT_INFO` / `GUIDE` 四选一，意图过滤主键 |
| `title` | 展示用，`rag_source` 事件里回传前端 |
| `sourceType` | `MANUAL` / `PRODUCT_AUTO` / `DOC` |
| `sourceId` | 商品 ID / 文档 ID |
| `productCategory` | `手机` / `笔记本电脑`…，商品类知识的二级过滤 |
| `chunkIndex` | 第几块，父块补全时定位相邻块 |

> ⚠️ **为什么强制字符串**：过滤最终变成 PG 的 jsonpath 比较。存成数字的 `knowledgeId: 33` 用 `knowledgeId == '33'` 匹配不到，存成字符串则表达式统一、不会踩类型坑。现有 `KnowledgeService.addToVectorStore` 已经是 `knowledge.getKnowledgeId().toString()`，延续这个写法即可。
> ⚠️ **安全**：`vectorStore.delete(String filterExpression)` 的表达式最终会**字符串拼接**进 SQL 的 jsonpath 字面量。**只允许拼数值型主键**（如 `knowledgeId`），绝不允许把用户输入拼进过滤表达式。

## 七、`KnowledgeService` 改造（P1 的主要工作量）

### 7.1 三处必须动的地方

| 现状 | 改成 | 原因 |
|------|------|------|
| `private final SimpleVectorStore vectorStore;` | `private final VectorStore vectorStore;` | 依赖接口而非实现，才能换成 `PgVectorStore` |
| `saveVectorStore()`（`vectorStore.save(File)`） | **整个方法删除**，所有调用点一并删 | `VectorStore` 接口没有 `save`；PG 写入即持久化 |
| `addToVectorStore()` 一条知识只存 **1 个 Document** | 先 `TokenTextSplitter` 分块，再逐块写 | 长知识不分块会超出 embedding 上下文，且检索粒度太粗 |

`vectorStoreLock`（`ReentrantReadWriteLock`）原本是保护 json 文件并发写的，换 PG 后由 upsert 保证幂等，可以删；保留也无害，但要在注释里说明它已不再必要，别让人误以为有并发语义。

### 7.2 关键代码

```java
private final VectorStore vectorStore;                       // 改：接口类型
private final SmartCsProperties props;                       // 新增：分块大小从这里读

/** 类上是 @RequiredArgsConstructor，构造不了带参对象，所以分块器放到 @PostConstruct 里建 */
private TokenTextSplitter splitter;

@PostConstruct
void initSplitter() {
    // 默认构造器是 800 token，必须显式给 chunk-size（首值 400，见 03 §7.1）；
    // 写死在代码里就进不了评测的 config_snapshot，参数实验无法归因（05 §6.6）
    splitter = TokenTextSplitter.builder()
            .withChunkSize(props.getRag().getChunkSize())
            .build();
}

/** 写入/覆盖一条知识的全部向量块 */
private void addToVectorStore(Knowledge k) {
    Document source = new Document(k.getTitle() + "\n" + k.getContent(), baseMetadata(k));
    // 注意：splitter.apply 产生的新 Document 会带随机 id，必须自己重编成业务键
    List<Document> chunks = splitter.apply(List.of(source));
    List<Document> toStore = new ArrayList<>(chunks.size());
    for (int i = 0; i < chunks.size(); i++) {
        Map<String, Object> md = new HashMap<>(chunks.get(i).getMetadata());
        md.put("chunkIndex", String.valueOf(i));
        toStore.add(Document.builder()
                .id("knowledge_" + k.getKnowledgeId() + "_c" + i)
                .text(chunks.get(i).getText())
                .metadata(md)
                .build());
    }
    vectorStore.add(toStore);   // ON CONFLICT (id) DO UPDATE：同 id 覆盖，重复执行安全
    log.info("知识已向量化 - knowledgeId: {}, chunks: {}", k.getKnowledgeId(), toStore.size());
}

private Map<String, Object> baseMetadata(Knowledge k) {
    Map<String, Object> md = new HashMap<>();
    md.put("knowledgeId", String.valueOf(k.getKnowledgeId()));
    md.put("category", k.getCategory() != null ? k.getCategory() : "");
    md.put("title", k.getTitle() != null ? k.getTitle() : "");
    md.put("sourceType", k.getSourceType() != null ? k.getSourceType() : "MANUAL");
    md.put("sourceId", k.getSourceId() != null ? String.valueOf(k.getSourceId()) : "");
    md.put("productCategory", k.getProductCategory() != null ? k.getProductCategory() : "");
    return md;   // 全部字符串，见 §6.2
}

/** 删除一条知识的全部块：块数未知，所以按元数据删而不是按 id 列表删 */
private void removeFromVectorStore(Long knowledgeId) {
    vectorStore.delete("knowledgeId == '" + knowledgeId + "'");  // knowledgeId 是数值主键，可安全拼接
    log.info("知识向量已删除 - knowledgeId: {}", knowledgeId);
}
```

改造后，`addKnowledge` / `updateKnowledge` / `deleteKnowledge` / `deleteKnowledgeBatch` / `syncProductKnowledge` / `disableProductKnowledge` 这些方法的**调用结构完全不用改**，只是底层换了实现——这也是为什么这次改造能控制在可接受的改动面内。

### 7.3 文档上传（`processDocumentAsync`）

现状用 `TextReader`，只能读纯文本。要支持 PDF/Word，加一个 reader 依赖：

```xml
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-tika-document-reader</artifactId>
</dependency>
```

```java
// 用 TikaDocumentReader 统一处理 txt/pdf/docx，替换原来的 TextReader
List<Document> documents = new TikaDocumentReader(new FileSystemResource(filePath.toFile())).get();
List<Document> chunks = splitter.apply(documents);
List<Document> toStore = new ArrayList<>();
for (int i = 0; i < chunks.size(); i++) {
    Map<String, Object> md = new HashMap<>(chunks.get(i).getMetadata());
    md.put("sourceType", "DOC");
    md.put("docId", String.valueOf(doc.getDocId()));
    md.put("title", doc.getFileName());
    md.put("category", "GUIDE");          // 上传文档默认归到指南类，可在页面上让用户选
    md.put("chunkIndex", String.valueOf(i));
    toStore.add(Document.builder()
            .id("doc_" + doc.getDocId() + "_c" + i)
            .text(chunks.get(i).getText()).metadata(md).build());
}
vectorStore.add(toStore);
doc.setChunkCount(toStore.size());
```

> ⚠️ `category` 只能取 `FAQ` / `POLICY` / `PRODUCT_INFO` / `GUIDE` 这四个值（前端知识库页面的下拉选项就是这四个）。**取值必须落在 Worker 的 `ragCategories` 里，否则这份文档写进去了却永远检索不到**——过滤是静默的，不报错、不空结果，只是这条知识从此隐身。默认给 `GUIDE` 是安全的（02 §四 已把 `GUIDE` 挂在售后域和政策域上），但更好的做法是上传页面让用户选一个。

> 只做 txt 就继续用 `TextReader`，不必引 Tika。要支持 PDF 才加——**别为了"看起来全"提前引依赖**。
>
> ⚠️ 现状 `processDocumentAsync` 里是 `new TokenTextSplitter()`（局部变量、默认 800 token）。这里要改成用 §7.2 那个 `@PostConstruct` 建好的字段，否则**上传文档和手工录入的块大小不一样**，评测快照里的 `chunkSize` 也就对不上文档那部分数据。

## 八、迁移与重建（一次性 + 可反复执行）

现有 `rebuildVectorStore()` 已经是"从 `ai_knowledge` 全量重建"的逻辑，换 PG 后**它就是迁移工具**，不需要额外写 ETL：

```
1. 起 PG（见 06 §1.1）
2. 启动应用 → initialize-schema=true 建表建 HNSW 索引
3. 跑一次 PG 侧索引脚本（§5.1）
4. 调 POST /ai/knowledge/rebuild-vector   → 全量向量化 ai_knowledge 中 status=1 的条目
5. 抽查：
   SELECT count(*) FROM vector_store;                                  -- 总块数
   SELECT id, left(content, 40) FROM vector_store LIMIT 5;              -- id 是否形如 knowledge_33_c0
   SELECT metadata FROM vector_store LIMIT 1;                          -- metadata 键是否齐全且全为字符串
6. 页面上问一个只有知识库才知道答案的问题，确认 rag_source 事件有来源
7. 确认无误后删除 D:/ruoyi/uploadPath/vectorstore.json（先备份）
```

重建是幂等的（同 id 覆盖），失败可以重跑。但要注意：**重建只写不删**——如果 `ai_knowledge` 里删过条目而向量库还留着旧块，需要先 `TRUNCATE public.vector_store;` 再重建。建议在 `rebuildVectorStore()` 里加一个 `truncate` 参数（默认 false），把这个语义显式化。

## 十一、验收与风险

**P1 验收清单**

- [ ] 应用启动日志出现 `初始化 PgVectorStore - table: public.vector_store, dimensions: 1024`
- [ ] `\d+ public.vector_store` 中 `id` 是 `text`、`embedding` 是 `vector(1024)`，且存在 `spring_ai_vector_index`
- [ ] 新增一条知识 → `vector_store` 出现 `knowledge_{id}_c0`；改内容 → 同 id 的 `content` 被覆盖而不是新增
- [ ] 删除一条知识 → 该 `knowledgeId` 的所有块消失
- [ ] 重启应用后检索照常（不再依赖任何本地文件）
- [ ] `DashboardController` 的统计接口仍然正常（证明主数据源没被抢）

**风险与规避**

| 风险 | 表现 | 规避 |
|------|------|------|
| 误用 starter | 启动时在 MySQL 上执行 `CREATE EXTENSION vector` 失败 | 只依赖 `spring-ai-pgvector-store` |
| id 非 UUID | 写入抛 `IllegalArgumentException: Invalid UUID string` | 固定 `idType(TEXT)`（§四） |
| 维度不匹配 | 写入报 `expected N dimensions` | 锁死 `dimensions=1024`；换模型必须重建表 |
| 主数据源被换 | 业务查询报"表不存在" | PG 数据源不加 `@Primary`；`JdbcTemplate` 用 `@Qualifier` 取 |
| `CREATE EXTENSION` 权限不足 | 启动失败 | 用 `pgvector/pgvector:pg16` 镜像的默认超级用户；托管 PG 需先由管理员建扩展，并把 `initialize-schema` 设为 false |
| 全文索引没建 | 混合检索的全文路慢或不生效 | §5.1 脚本纳入部署检查清单 |
