# 00 · 总体设计方案（求职作品 · 务实可落地）

> 定位：**求职面试作品项目**（面向 Java 后端 / AI Agent 开发岗）。核心标准：**能真实跑起来、能量化评测、能给面试官讲清楚且经得起追问。**
> 本文是整套设计文档的**总纲** —— 改需求先改这里，其余子文档见文末索引。
> 本文档不排时间线。所有阶段按**依赖关系**串行，每步有独立验收标准。

---

## 一、现状与改造动机

### 1.1 现状

RuoYi 3.9.1 + Spring Boot 3.5.8 + Spring AI 1.0.0 GA 的**单智能体**数码商城客服（"小智"）：
一个 `ChatClient` 挂 **1 个大 System Prompt + 38 个 `@Tool` 工具 + Naive RAG(SimpleVectorStore) + DatabaseChatMemory + SSE**。

工具实际分布（`ruoyi-ai/src/main/java/com/ruoyi/ai/mcp/`，共 **38** 个 `@Tool` 方法）：

| 工具类 | 数量 | 方法名 |
|--------|------|--------|
| `ProductMcpTools` | 5 | searchProducts / getProductDetail / compareProducts / recommendProducts / getProductReviews |
| `CartMcpTools` | 6 | viewCart / addToCart / removeFromCart / updateCartQuantity / clearCart / checkoutFromCart |
| `OrderMcpTools` | 6 | queryOrder / queryUserOrders / queryLogistics / cancelOrder / confirmReceive / payOrder |
| `TicketMcpTools` | 6 | createTicket / queryTicket / queryUserTickets / escalateToHuman / replyTicket / closeTicket |
| `ReviewMcpTools` | 3 | submitProductReview / checkReviewStatus / queryMyReviews |
| `UserMcpTools` | 7 | queryUserInfo / queryUserAddresses / queryDefaultAddress / setDefaultAddress / addAddress / updateAddress / deleteAddress |
| `NotificationMcpTools` | 5 | queryUnreadNotifications / getUnreadCount / markNotificationRead / markAllNotificationsRead / queryNotificationHistory |

> ⚠️ 面试时报数字用 **38**，不要说"20+"，也不要说"每个 Agent 只持 2-3 个工具"——那是工具**组**数，不是工具数。真实数字见 §02。

### 1.2 两个真实的改造动机（不是为了堆技术）

1. **可靠性缺口**：审计表 `ai_chat_turn_audit` 现有 **82 轮**对话，其中 **5 轮**的回复是"抱歉，系统暂时繁忙，请稍后再试"（失败率 **6.1%**），而且 `audit_id` 57~60 是**同一个会话里连续四次**问同一句话、连续四次失败。当前**没有任何指标能量化它**——Dashboard 上只有工具成功率和 RAG 命中率，用户连着失败四次这件事在指标里完全看不见。
   这 5 轮的耗时是 13523 / 13356 / 12853 / 12967 / 13409 毫秒，**全部落在 12.8~13.5 秒这个很窄的区间里**。对着 `RetryConfig` 算一下就知道成因：`maxAttempts=3`、指数退避 1s→2s（退避总计 3 秒），也就是 3 次模型调用共耗约 10 秒、单次约 3.3 秒就失败了。**这是"快速失败 3 次后重试耗尽"，不是"卡住等超时"**——两者的修法完全不同，所以指标必须把 `retry_count` / `failure_count` / `is_timeout` 分开记（05 §3.1）。顺带量出来的另一个数：这 82 轮的耗时 **p95 约 29 秒、最慢一轮 96.9 秒**，这就是"延迟优先"（§二）不是空话的依据。
2. **工具面过大**：38 个工具塞进一个 `ChatClient`，模型选错工具的概率随工具数上升，且大 prompt 挤占上下文。

这两条构成"我从真实数据里发现问题 → 因此设计了可观测性和领域隔离"的叙事，比"我想用多智能体"有说服力得多。

### 1.3 改造目标

1. **能用**：部署后真实可对话、可查商品/订单/售后、可上传文档提问。
2. **可测**：在线指标实时监测；离线黄金集能算出改造前后的检索与工具指标对比。
3. **可讲**：架构决策、模式命名、指标闭环、调优路径能讲清并经得起追问。

## 二、核心取舍：延迟优先

**已确认：延迟 > 质量。** 两者都重要，冲突时保用户体验。这条取舍直接决定了下面一串设计，面试时这是一个完整的工程判断叙事。

| 决定 | 理由 |
|------|------|
| **查询改写（multi-query）不做** | 每次多 1 次 LLM 调用，收益不确定，与延迟优先直接冲突 |
| **Evaluator 做异步抽检，不阻塞回复** | 同步纠错要多 1~2 次模型调用，会把 p95 拉高一倍以上 |
| **只有跨域意图才走 Supervisor 多轮编排** | 80% 单域请求不该为多轮编排付延迟和 token |
| **混合检索（向量 + 全文）保留** | 两路都在 PG 内一次往返完成，延迟增加可忽略 |
| **重排条件启用** | 先看黄金集 Precision 数字再决定；启用时优先 `text-rerank` API（一次 HTTP）而非 LLM-judge（一次大模型） |
| **`intent` 事件第一时间推给前端** | 路由完成即推"导购助手正在处理…"，直接改善**感知**延迟 |
| **规则路由优先于 LLM 路由** | 规则命中零延迟零成本，同时降低"系统繁忙"概率 |

> 面试话术："这个系统我定的取舍是延迟优先。所以查询改写我砍了、Evaluator 改成异步抽检、Supervisor 只在跨域请求上启用。每一条我都能说出它省下了几次模型调用。"

## 三、目标架构

### 3.1 一句话说明

一次请求先经 `IntentRouter` 判定意图：**闲聊 / 转人工不进 Agent 栈**直接回；**单域请求直连**对应 Worker；**跨域请求**交给 `SupervisorAgent`，由它把 Worker 当作 `@Tool` **串行**调用。回复推完之后，`Evaluator` **异步抽检**打分入库，不阻塞用户。

### 3.2 结构图

```
POST /ai/chat/stream-ticket ──► ticket(Redis,60s,一次性)
        │
GET  /ai/chat/stream?message=&sessionId= (SSE)
        │
        ▼
  ChatOrchestrator                             ← 新增，替代 ChatService 里的直调 chatClient
        │
        ├─① IntentRouter.route()               ← 规则命中=0 次模型调用；未命中才用 router 模型
        │     │
        │     ├─ CHITCHAT / HUMAN_HANDOFF ──► 直接回复/建工单，结束（省一次大模型调用）
        │     ├─ 单域(PRODUCT/ORDER/AFTERSALES/ACCOUNT/KNOWLEDGE) ──► ② 直连 Worker
        │     └─ CROSS_DOMAIN ──────────────► ③ SupervisorAgent（Worker as @Tool，上限 3 次）
        │
        ├─② Worker.execute()                   ← 自己的 ChatClient：领域 prompt + 领域工具 + HybridRagAdvisor
        │        └─ 内部工具循环（工具预算守卫：单轮工具调用上限 8 次）
        │
        ├─④ 结果汇总 → SSE 推送 text / rag_source / card_data / message_id / [DONE]
        │
        ├─⑤ AuditService.recordTurn(... intent, agentId, retry/failure/timeout ...)   异步
        │
        └─⑥ Evaluator.spotCheck()              异步抽检（默认 10% 采样），结果写审计，不影响本轮回复
```

### 3.3 与现状最大的三个差别

| | 现状 | 改造后 |
|--|------|--------|
| 工具面 | 1 个 ChatClient 挂 38 个工具 | 5 个 Worker，单个 ChatClient 面对 **1~13** 个工具 |
| 检索 | 每轮 **2 次** embedding + 2 次向量检索（`RagSourceCapturingAdvisor` 与 `QuestionAnswerAdvisor` 各查一次），topK=3 | 合并成 **1 次**；topK 可调；支持元数据过滤与混合检索 |
| 可观测 | 只有 RAG 命中率 / 工具成功率 | 加 失败率 / 重试率 / 超时率 / p95，以及离线黄金集 Recall\@K、MRR、Tool Accuracy |

> 「每轮 2 次检索」是读代码确认的：`AiConfig` 同时注册了 `RagSourceCapturingAdvisor(vectorStore,3,0.5)` 和 `QuestionAnswerAdvisor(topK=3,threshold=0.5)`，两者各自独立调用 `vectorStore.similaritySearch`。合并后每轮省 1 次 embedding HTTP 调用 + 1 次向量检索，这是**纯收益的延迟优化**，也是面试里很具体的一个点。

## 四、关键决策记录（ADR）

每条都写清**为什么这么定**和**代价**。面试被追问时，照这张表答。

| # | 决策 | 依据（已在本仓库/源码中核实） | 代价 / 风险 |
|---|------|------------------------------|------------|
| 1 | 向量库换 **pgvector**，且用非 starter 的 `spring-ai-pgvector-store` + **手写 Bean** | RuoYi 的 `DruidConfig.dataSource()` 是 `@Primary`（`dynamicDataSource`）。pgvector starter 的自动配置会拿**主 JdbcTemplate（MySQL）**去建向量表，必然失败。手写 Bean 用独立 PG `JdbcTemplate`，绕开这个坑 | 多一个 PG 依赖；配置要自己写（代码见 §01） |
| 2 | 向量表 **id 用 `PgIdType.TEXT`**，不用默认 UUID | `PgVectorStore.convertIdToPgType()` 在 UUID 模式下执行 `UUID.fromString(id)`；现有 `KnowledgeService` 传的 id 是 `"knowledge_33"`，UUID 模式下**必抛 IllegalArgumentException**。改 TEXT 后可继续用业务键 `knowledge_{id}_c{n}`，天然幂等（`ON CONFLICT (id) DO UPDATE`） | 与"标准姿势"略有差异，需在文档里解释 |
| 3 | 两个 RAG Advisor 合并为一个 `HybridRagAdvisor`（实现 `BaseAdvisor`） | 现状每轮检索两次（见 §3.3 注）；`QuestionAnswerAdvisor` 源码给出了标准增强姿势：`request.mutate().prompt(prompt.augmentUserMessage(text)).context(ctx).build()`，照抄即可 | 自己维护一个 Advisor（约 120 行） |
| 4 | 领域隔离：**5 个 Worker**，各自一个 `ChatClient` | 38 个工具塞一个 prompt，选错工具概率随工具数上升 | 多 5 个 Bean；跨域请求要靠 Supervisor 兜 |
| 5 | 各 Worker 的 `ToolCallbackProvider` **在 Bean 方法内联构建**，全局只保留 `AiConfig` 里那**一个** `ToolCallbackProvider` Bean | MCP Server 自动配置会收集**所有** `ToolCallbackProvider` 类型的 Bean。多声明就会把同名工具重复暴露给 MCP 端点 | 需要在代码里写注释提醒，别手滑改成 `@Bean` |
| 6 | 路由 = **规则优先 + LLM 兜底** | 规则命中零延迟零成本，直接压低"系统繁忙"概率 | 规则表要维护；歧义句仍需模型 |
| 7 | 跨域用 **Supervisor（Worker as `@Tool`）**，且**串行**调用、上限 3 次 | 项目已验证 `@Tool` + `MethodToolCallbackProvider` 链路可用，复用零新风险。**必须串行**：`ChatContext` 是 `ThreadLocal`，并行调用会丢 sessionId/emitter，导致工具事件推不出、审计缺字段 | 跨域请求延迟明显更高（多轮模型调用），所以只对跨域启用 |
| 8 | **不做**查询改写 / multi-query | 与"延迟优先"直接冲突（每次多 1 次 LLM 调用） | 口语化提问的召回靠元数据过滤 + 混合检索补 |
| 9 | Evaluator **异步抽检**（默认采样 10%） | 同步纠错要多 1~2 次模型调用，p95 至少翻倍 | 不能实时纠错，只能事后发现问题 |
| 10 | 单轮**工具预算守卫**（默认 8 次）用 AOP 切 `com.ruoyi.ai.mcp` 包实现 | Spring AI 1.0.0 的内部工具执行循环没有暴露"最大轮数"配置项；`ChatContext.getToolCallNames()` 已经在 38 个工具里逐个埋好点，直接用它计数最省事 | 切面要处理好"超限后返回什么"（返回提示字符串，不抛异常） |
| 11 | 评测/审计/黄金集表留在 **MySQL**，向量只在 **PG** | 审计要和 `ai_chat_message`、`ai_tool_call_log` 关联查询 | 两个库都要备份 |
| 12 | 模型型号全部**外置成配置项**，默认值 = 当前在跑的 `qwen3.5-plus-2026-02-15` | 现状写死在 `application.yml`；路由/评测想换便宜档位时不该改代码 | 换档位前要确认账号里该型号已开通 |

## 五、落地顺序（依赖关系，**不含时间承诺**）

P 编号只表示**谁必须先做完**，不代表工期。每步都有独立验收标准，做完一步系统仍是可运行的。

```
P-1 版本控制 + 备份 + 30 条黄金集基线（无依赖，开工第一件事）
 └─ P0 环境地基（路径外置 / 起 PG / 修超时）
     ├─ P1 pgvector 落地
     │   ├─ P2 RAG Advisor 合并
     │   ├─ P5 混合检索（全文 + RRF）      ← 还需 P2
     │   └─ P6 离线评测管道                ← 只需 P1，不必等 P5
     └─ P3 审计与在线指标                  ← 可与 P1/P2 并行

P4 路由 + Worker + 编排                    ← 需 P2 + P3
 └─ P7 Supervisor + 异步抽检 + HITL
     └─ P8 Docker 化                       ← 需以上全部
```

> P6 的位置容易画错：它挂在 P1 下面，**不在 P5 后面**。评测管道只要检索层能跑就能建，越早建越有基线可比——排到 P5 之后，P5 自己就没有对照组了。

| 阶段 | 做什么 | 依赖 | 验收标准（可自测） |
|------|--------|------|-------------------|
| **P-1** | 项目纳入 git；`mysqldump` + 备份 `vectorstore.json`；筛 30 条真实提问录入 `ai_eval_golden`，并抄下改造前的在线指标 | — | 有第一个 commit 且密钥未进仓库；有一份可回滚的数据备份；`ai_eval_golden` 有 30 条条目级标注（**离线基线要等 P6 才跑得起来**，P-1 只负责把语料和改造前的数字固定住） |
| **P0** | 硬编码路径外置（`ruoyi.profile`、`smart-cs.upload.path`、`smart-cs.vector-store.path`）；起 PG(pgvector)；PG 数据源与 `JdbcTemplate` 通；搭测试骨架 | — | 应用启动无报错；`select 1` 能打到 PG；`ruoyi.profile` 走环境变量后上传功能仍正常；`mvn -pl ruoyi-ai -am test` 能跑通 |
| **P1** | `PgVectorConfig` + `KnowledgeService` 从 `SimpleVectorStore` 切到 `VectorStore`；`/ai/knowledge/rebuild-vector` 全量重建 | P0 | `vector_store` 表有数据且 `id` 形如 `knowledge_33_c0`；知识条目增/改/删后向量同步正确；重启后检索仍正常（不再依赖 json 文件） |
| **P2** | `HybridRagAdvisor`（先只做向量路）替换现有两个 Advisor；接元数据过滤 | P1 | 单轮日志里 embedding 请求**只出现一次**；`rag_source` 事件仍正常；同一问题命中的知识与 P1 基线一致或更好 |
| **P3** | `ai_chat_turn_audit` 扩字段；`AuditService`/编排层埋点；Dashboard 新增 4 个指标 | P0 | 连续对话 10 轮后，审计表 `intent`/`agent_id`/`retry_count`/`is_timeout`/`duration_ms` 有值；`/ai/dashboard/ai-metrics` 返回失败率/重试率/超时率/p95 |
| **P4** | `IntentRouter` + 5 个 Worker `ChatClient` + `ChatOrchestrator` 直连编排 + `intent` SSE 事件 + 工具预算守卫 | P2, P3 | 问"推荐手机"命中 `sales-advisor`；问"我的订单"命中 `order-service`；问候语不触发任何模型调用（看日志）；审计里 `agent_id` 正确 |
| **P5** | PG 全文路（`tsvector`）+ RRF 融合 | P1, P2 | 搜型号/SKU（如 `RK87`）能命中；黄金集 Recall\@8 不低于 P2 基线（评测 K 定死为 8，见 05 §4.2） |
| **P6** | 黄金集（起步 40~50 条，随抽检回流补到 100 条）+ `EvaluationJob` + `ai_eval_result` + 评测接口 | P1（基线越早越好） | 能一键跑完并落库；能打印"改造前 vs 改造后"同集对比表 |
| **P7** | `SupervisorAgent`（跨域）+ 异步 `Evaluator` 抽检 + HITL 待确认操作（`ai_pending_action`） | P4 | "查下我的订单，再推荐个手机壳"能一次答完两件事且 Worker 调用 ≤3 次；退款类操作先出确认单、用户确认后才执行 |
| **P8** | `docker compose` 一键起 MySQL/Redis/PG/后端/Nginx | 以上 | 全新机器上 `docker compose up` 后能登录、对话、上传文档提问 |

> **建议**：P-1 那 30 条黄金集是整份计划里最容易被跳过、也最不该跳过的一步。没有改造前的基线，后面所有"提升了多少"都说不出数字——而基线一旦动手改代码就再也测不到了。操作步骤见 07 §1.3。

## 六、非目标（明确不做，避免摊子失控）

- 多模态（图片/语音理解）：`smart-cs` 的图片链路不在本轮范围。
- 中文分词插件（`zhparser` / `pg_jieba`）：需要自定义 PG 镜像，部署摩擦大于收益。中文语义交给向量路。
- 分布式 Agent 框架、K8s、消息队列削峰：作品规模用不上，反而增加讲解负担。
- 模型微调 / 自训练 embedding：成本与收益不匹配。
- 前端大改：只加 `intent`/`agent_switch` 事件展示与评测结果页。

## 八、风险台账

| 风险 | 触发条件 | 应对 |
|------|----------|------|
| pgvector starter 抢主数据源 | 误加 `spring-ai-starter-vector-store-pgvector` | 只加非 starter 模块 + 手写 Bean（§01） |
| 文档 id 不是 UUID 导致写入报错 | 用默认 `PgIdType.UUID` | 固定 `idType(TEXT)` + 业务键（§01） |
| MCP Server 重复暴露工具 | 把 Worker 的 provider 声明成 `@Bean` | 内联构建，代码里写注释（§02） |
| Supervisor 并行调 Worker 丢上下文 | 用 `CompletableFuture` 并行 | 强制串行（§02 ADR-7） |
| 工具循环打爆 token | 模型反复调工具 | `ToolBudgetAspect` 单轮上限（§02） |
| 多一个模型调用把 p95 拖高 | 加了同步 Evaluator / 查询改写 | 已在 §二 明确砍掉 |
| 改造后检索反而变差 | 直接上线不比对 | 每阶段过黄金集，退不回就回滚参数（§05） |
| **类别过滤把知识过滤没了** | Worker 的 `ragCategories` 漏掉某个真实存在的类别（`FAQ` 就差点被漏掉） | 过滤取值必须与 `ai_knowledge.category` 的四个真实枚举逐一对齐（§02 §四）；过滤是静默的，只能靠核对，测不出来 |
| SQL 重复执行报错 | 迁移脚本不幂等 | 全部用 `information_schema` 动态判断（§05） |
